# 测试动态数据与引用规范

- 日期：2026-11-06
- 状态：presence 用例及相关工具已按本规范整改；其他用例保留原入口。本文示例用于说明约束，实际可执行用例见 `testing/flows/5.0.0-multi-presence-positive.yaml`。
- 适用范围：`5.0.0` 工作树的单设备、多设备自动化测试。
- 目标：让每个动态值的来源、设置时机、读取条件和生命周期明确，避免隐含依赖、跨轮串数据和结果覆盖。

## 1. 核心规则

| 编号 | 规则 |
|---|---|
| D01 | 动态数据分为设备、账号、业务数据三类，统一通过 `$global` 引用。 |
| D02 | `global` 是运行环境保留名称；用例不得用 `as`、`set`、循环变量覆盖，也不得任意写入其内容。 |
| D03 | 每类数据有指定提供者和使用者；`global` 是本轮数据视图，不是任意可写的共享变量。 |
| D04 | 每轮建立独立上下文。准备数据和运行结果都归属本轮，禁止默认继承上一轮结果。 |
| D05 | 设备准备、数据准备、执行编排职责分离；初始化和登录仍是流程中的显式命令。 |
| D06 | 准备数据在执行前固定；初始化配置采用本轮快照，修改后必须重启 App 并重新初始化才生效。 |
| D07 | API 结果只能在对应调用结束并完成绑定后读取；事件只有经过等待、匹配和绑定，才成为后续步骤引用的目标事件。 |
| D08 | 每次调用结果和每条监听事件分别保存；禁止用隐含的“上一条”“最新一条”代替明确绑定，禁止重复执行时静默覆盖历史。 |
| D09 | 路径错误、结果尚未产生、前置失败和合法 `null` 必须区分；缺失引用不得静默转换成 `null`。 |
| D10 | 解释器只处理通用路径、绑定和流程依赖；不解释账号、消息、presence 等业务字段。 |
| D11 | YAML 管流程，JSON 装数据。JSON 的 `steps` 保持命令格式；其他顶级数据由各自的消费工具解释，不自动注入 `$global`。 |

命令及其参数保持在同一个 JSON 命令对象中，不拆分成独立的命令文件与参数文件。顺序、并发、等待、条件和延时由 YAML 控制。

### 1.1 用例 JSON 容器规则

根节点必须是 JSON 对象。以 [presence 用例 JSON](../flows/scripts/5.0.0-multi-presence-positive.json) 为例，数据准备声明与命令放在一起：

```json
{
  "data": {
    "accounts": {"alice": 0, "bob": 1},
    "unique": {"presenceDescription": "presence-"},
    "distinctAccounts": true
  },
  "steps": [
    {
      "id": "publish",
      "api": "ChatPresenceManager.publishPresence",
      "params": {"desc": "$global.biz.input.presenceDescription"}
    }
  ]
}
```

| 顶级节点 | 提供者／使用者 | 规则 |
|---|---|---|
| `steps` | 用例作者／命令加载与派发模块 | 继续使用原有命令数组；`id`、`api`、`params`、`expect` 保持在一个对象中，YAML 按命令 `id` 引用。 |
| `data` | 用例作者／`prepare_data` | 可选的数据准备声明对象；字段见下表。解释器不处理该节点。 |
| `init`、`login` | 旧脚本作者／旧 AutoMode 入口 | 保留原有含义，不改作自定义数据；HTTP 流程仍显式执行初始化、登录命令。 |
| 其他顶级节点 | 作者／对应工具 | 可承载对象、数组、标量等 JSON 数据。消费工具需明确其语义；命令加载器忽略这些节点，不执行、不转换成流程变量、不自动注入 `$global`。 |

`data` 是当前数据工具识别的准备声明，不是可任意写入的运行上下文：

| `data` 字段 | 形式与含义 | 生成结果／使用者 |
|---|---|---|
| `accounts` | 可选的角色 → 本地配置账号列表下标（从 0 开始）；非空时须完整覆盖所有角色。省略或空对象时保留按角色顺序分配的旧行为。 | `$global.account.<role>`，供登录命令等引用。 |
| `unique` | 可选的字段名 → 字符串前缀；每轮为每个字段追加 16 字节安全随机数的十六进制表示。 | `$global.biz.input.<字段>`，各角色共享，供命令参数及事件匹配使用。 |
| `distinctAccounts` | 可选布尔值；`true` 要求角色账号互不相同，缺省 `false`。 | 准备阶段校验，不新增运行变量。 |

`data` 未声明则沿用旧行为；声明为 `null`、数组或标量报错。`data` 内未知字段由数据工具拒绝；容器其他顶级节点可自行组织，但增加节点不代表已有工具会消费它。

装载与兼容规则：

1. `prepare_data --flow` 从 YAML 的 `agents.*.script` 定位 JSON，路径相对 YAML 所在目录。多个角色引用同一个实际文件只作为一份声明。
2. 一条流程自动发现最多一份数据准备声明；不合并多个 JSON 的 `data`。旧的相邻 `<flow>.data.json` 仍兼容，但它与内嵌 `data` 同时存在也报冲突，即使内容相同。
3. 显式 `--data <json>` 保留旧语义：该文件本身是完整准备声明，替代自动发现结果，不与内嵌或相邻声明合并。没有任何声明时使用 `{}`。
4. 命令格式、`init`／`login`、其他旧字段的原有行为不变。HTTP 流程新增等待仍写 YAML，不新增 JSON 控制字段；旧 AutoMode 延时字段继续由旧入口处理。
5. 选中的声明先保存为 `testing/tmp/<run-id>/data-declaration.json`，准备完成的具体值仍保存在同目录 `data.json`，正式执行前再组合成 `global.json`。删除独立的源声明文件不等于删除运行数据或证据。

## 2. 数据分类与引用入口

| 入口 | 内容 | 示例 |
|---|---|---|
| `$global.device.<role>` | 逻辑角色对应的物理设备和控制连接信息 | `$global.device.deviceA.platform` |
| `$global.account.<role>` | 为该设备角色分配的账号和登录凭据 | `$global.account.deviceA.userId` |
| `$global.biz.config` | 本轮初始化配置快照 | `$global.biz.config.initConfig` |
| `$global.biz.input` | 用例输入，如消息正文、订阅时长、本轮唯一标识 | `$global.biz.input.messageText` |
| `$global.biz.result.<binding>` | 某次 API 调用的完整结果 | `$global.biz.result.send_message.data.msgId` |
| `$global.biz.event.<binding>` | 某次等待所匹配事件的 payload | `$global.biz.event.received_message.msgId` |

- `deviceA` 是流程中的逻辑角色，不是模拟器名称，也不是账号 ID。设备工具建立逻辑角色到真机或模拟器的映射。
- `$global.account.deviceA` 表示为 deviceA 分配的账号。同一账号可以分配给多个设备；分配成功不代表已登录成功。
- `initConfig`、`messageText`、`msgId` 是数据字段，不是解释器关键字。上表的 `initConfig` 示例表示共用配置，不要求不同设备必须使用相同配置。
- `send_message`、`received_message` 是明确的结果绑定名称，不是“最近一条消息”，也不等同于命令库中的可重复执行命令 ID。
- 命令结果保留完整返回结构，因此通过 `.data` 访问业务返回值；事件绑定直接访问 payload。事件来源、顺序等元信息另随原始记录保留，不混入 SDK payload。
- `$global` 表示内存中的运行数据视图，不等于每次引用都重新读取某个 JSON 文件。准备数据可以从文件加载，结果和事件在执行过程中产生并保存。
- 不同时引入 `$var` 作为另一套同义数据入口。循环元素、条件状态等流程变量仍由流程作用域管理，不放进 `$global.biz`。

## 3. 提供者、使用者与写入权限

| 数据 | 数据提供者 | 保存／装载者 | 使用者 | 更新约束 |
|---|---|---|---|---|
| 设备信息 | `setup_devices` | 编排脚本组织运行器装载 | 运行器的连接、派发和取证模块 | 本轮设备准备完成后固定 |
| 账号与角色分配 | `prepare_data` | 编排脚本组织运行器装载 | 登录命令、需要用户身份的业务命令和断言 | 执行前确定；实际登录状态由命令结果确认 |
| 初始化配置 | `prepare_data` | 运行器装载固定快照 | 初始化命令、配置核对步骤 | 不随磁盘文件变化而更新 |
| 用例输入 | 用例声明、`prepare_data` | 运行器装载 | 命令参数、条件和断言 | 执行前准备；由前置结果产生的值通过结果引用传递 |
| API 返回结果 | App 执行端 | 运行器接收、记录并绑定 | 明确依赖该次调用的步骤，以及失败分析分支 | 每次调用分别记录；原始结果不可被断言改写 |
| 原始监听事件 | App 监听器 | App 持续留存；运行器等待时读取、收尾时分页归档 | 等待与匹配逻辑、证据分析 | 追加记录，不覆盖历史事件 |
| 已匹配事件绑定 | 运行器的等待与匹配逻辑 | 运行器 | 等待成功后的依赖步骤 | 绑定到明确事件，并能追溯原始记录 |
| 流程变量 | `set`、`for` 等流程节点 | 解释器 | 对应作用域内的流程节点 | 不得覆盖系统名称，不得与业务结果混用 |

职责边界：

- `setup_devices` 只准备设备和控制连接，不读取账号来生成登录参数，不生成初始化配置或业务标识。
- `prepare_data` 准备账号、Token、资源、配置及角色分配，不安装 App，不操作设备连接。
- `run_flow`、`run_single` 是组合入口：调用基础工具、检查产物、建立运行上下文、启动执行、组织报告与清理。数据生成逻辑归对应基础工具。
- 业务命令只使用声明所需的数据；设备控制凭据由控制通道使用，不作为 SDK 业务参数注入。
- `device/account/biz` 是测试运行环境的数据组织约定。解释器可以读取这些路径，但不得内置 IM 账号准备、SDK 初始化或消息字段转换逻辑。

## 4. 设置时机与可读条件

| 阶段 | 设置或保存的内容 | 设置完成条件 | 此时不能据此认定 |
|---|---|---|---|
| S0 建立本轮运行 | 运行标识、项目内运行目录 | 编排入口建立独立运行上下文 | 前一轮结果仍然有效 |
| S1 准备数据 | 账号分配、配置快照、用例输入、准备资源 | `prepare_data` 成功且数据校验通过 | SDK 已初始化、账号已登录 |
| S2 准备设备 | 角色到设备的映射、可用连接和控制凭据 | `setup_devices` 确认对应设备就绪 | 业务 API 已可正常调用 |
| S3 正式执行前 | 汇总初始 `$global` 数据视图 | 角色、数据、设备对应关系检查通过 | API 返回结果或监听结果已经存在 |
| S4 显式初始化、登录 | 初始化、登录的实际执行结果 | 相应命令结束并保存结果 | 仅凭“准备配置成功”认定初始化成功 |
| S5 API 调用结束 | 本次完整返回结果及断言结论 | 结果记录与绑定完成 | 调用结束就等于断言通过 |
| S6 监听通知到达 | 原始事件记录 | 收集到事件并保存 | 任意同名事件都属于本轮目标动作 |
| S7 等待事件成功 | 已匹配事件的引用绑定 | 来源与业务匹配条件满足 | 仅凭事件顺序号认定业务归属 |
| S8 本轮结束 | 报告、运行数据与证据归档 | 执行收尾并记录清理情况 | 下一轮可以继续读取本轮内存绑定 |

S1、S2 是职责独立的准备阶段，均完成后才能进入 S3。S6 在运行中持续发生，可能早于 S5；它不是必须排在 API 返回之后的串行阶段。

运行中的流程变量由对应 `set`、`for` 节点设置，只在规定作用域内可读。准备脚本不能预先填充未来调用结果或伪造监听结果。

### 初始化配置

配置在初始化之前就存在。初始化之后可引用的是本次实际传入初始化命令的配置快照，并通过调用结果确认是否初始化成功。若初始化使用了覆盖值，证据必须能还原最终传入的配置，而非仅保留覆盖前的源文件。

本方案不支持热更新初始化配置。修改本地文件不改变已运行 App 的配置；变更配置后必须重启并重新初始化，不能将新文件值冒充本次生效值。

### API 结果与事件

- API 失败结果同样保存；成功或失败信息与断言是否通过分别记录。正常依赖链按失败策略处理，显式失败分析可以读取失败结果。
- 超时只表示逻辑等待结束，不保证外部操作停止。迟到结果应作为证据保留，不能把已经结束的步骤重新判为成功。
- 监听收集不能等到执行 `wait_event` 才开始。通知可能在发送命令返回前到达，必须保留并允许后续等待匹配。
- 原始事件可立即用于排查；供后续命令引用的目标事件必须由明确的等待和匹配产生绑定。
- 历史服务端通知也可能在本轮登录后到达。新 App 实例或较新的事件序号不能单独证明它属于本轮，应使用账号、消息 ID、本轮标识等场景匹配条件。

## 5. 引用与失败边界

| 情况 | 规则 |
|---|---|
| 引用替换 | 参数值使用完整引用字符串；保留原始数据类型，不做字符串内部插值或任意代码求值 |
| 嵌套访问 | 使用点路径读取对象字段，使用数字下标读取列表；对象和列表本身也可整体传递 |
| 配置或路径拼错 | 能静态检查的在执行前报错；运行时才可确认的在派发依赖命令前报错，不向 SDK 传入伪造的 `null` |
| 结果尚未产生 | 由流程显式建立先后、同步或等待关系；读取引用本身不隐式等待 |
| 前置调用失败 | 保存真实结果，按既定失败策略阻断受影响的链；不把它当作普通字段缺失，也不停止无关用例 |
| 合法返回 `null` | 路径确实存在且值为 `null`，与缺失路径区分；是否满足预期由断言决定 |
| 重复调用、循环与并发 | 必须区分具体调用和事件绑定；不得让完成顺序决定某个隐含“最新结果”的含义 |
| 本轮结束 | 内存上下文结束；已保存数据用于追溯，不自动成为下一轮输入 |

不得因 SDK 缺陷改写结果、放宽正确断言或修改正确用例。用例、工具、环境与 SDK 问题需要分别记录和分析。

## 6. 示例：A 发送消息，B 回执，A 收到回执

以下仅说明数据关系和设置时机，不定义新的可执行 YAML 语法。

| 顺序 | 动作 | 使用的数据 | 新产生的数据 |
|---|---|---|---|
| 1 | 准备设备、账号与业务输入 | 用例的设备角色、账号分配、消息内容 | 初始 `device`、`account`、`biz.config`、`biz.input` |
| 2 | A、B 初始化并登录 | 各自账号、初始化配置 | 各次初始化、登录结果 |
| 3 | A 向 B 发消息 | B 的用户 ID、消息正文 | A 的发送结果，绑定为 `send_message` |
| 4 | 等待 B 收到目标消息 | 发送方身份、消息 ID或本轮标识等匹配条件 | B 收到的事件 payload，绑定为 `received_message` |
| 5 | B 发已读回执 | 已匹配接收事件中的实际消息数据 | 本次回执 API 结果 |
| 6 | 等待 A 收到目标已读回执 | 目标消息 ID、回执方身份等匹配条件 | A 的已读回执事件绑定 |

如果事件匹配依赖的发送结果尚未绑定，必须由流程安排结果就绪后的匹配，并保留期间已到达的事件；不能丢弃该事件后期待它再次到达。

典型引用：

```text
发送目标用户：$global.account.deviceB.userId
发送消息正文：$global.biz.input.messageText
发送成功后的消息 ID：$global.biz.result.send_message.data.msgId
B 收到的消息 ID：$global.biz.event.received_message.msgId
```

## 7. 项目内运行产物与可追溯性

运行数据必须能在项目内按本轮标识找到。不能把系统 `/tmp` 作为唯一的数据或证据来源。

沿用现有目录分工作为整理基础：

- `testing/tmp/<run-id>/`：项目内临时目录，保存准备数据、设备映射、实际执行参数、原始结果和事件等运行证据。
- `testing/reports/<run-id>/`：该轮结论、可分享的参数与证据摘要，并能定位对应运行数据。
- 两者均不由 Git 管理；账号 Token、控制凭据保留在受限的本地运行产物中，报告中脱敏。
- 排查需要能追踪“引用路径 → 来源 → 实际值 → 使用步骤”。只保存最初配置文件不足以解释执行中产生的值。
- 临时目录可清理，但应在所需证据归档、资源归属及清理情况明确之后；不能因为存在其他轮次的报告就删除本轮唯一证据。

presence 运行产物已落地：文件列表、保存内容及权限见 [脚本说明](../scripts/README.md#本轮数据与证据)。原始事件与引用值保存在项目内 tmp，报告提供对应目录索引；不会自动删除 tmp。

## 8. 现状与落地边界

presence 用例已使用 `$global`。运行器通过 `--globals-file` 装载 `initial` 和 `outputRoots`，后者仅开放结果与事件区域。现有其他用例继续使用 `$config`、`$agents`、`$inputs`、`$step`、`$prev`；未对它们进行批量迁移。

旧写法需要按数据含义迁移，不能只改前缀：

| 现有写法 | 按本规范归类 |
|---|---|
| `$config`、`$agents` 中的账号字段 | `account` |
| `$config.initConfig`、其他角色中的初始化配置 | `biz.config` |
| `$inputs` 中的用例参数 | 来源可能是 `biz.input`、调用结果或事件；需明确来源，参数传递方式在迁移时统一 |
| `$step`、命令 `as` 绑定 | 明确到本次调用的 `biz.result` |
| 事件 `as` 绑定 | 明确匹配的 `biz.event` |
| `$prev` | 改为明确的调用结果引用，不保留隐含“上一条”依赖 |
| `set`、`for` 变量 | 流程状态，不直接迁入业务数据 |

当前采用现有 `as` 字段指定完整目标路径，如 `as: global.biz.result.original`。同一命令可以重复执行，但结果路径必须不同；重复路径直接拒绝，不提供隐含最新值。事件数组匹配复用 `checks/containsItem`，只绑定符合条件的目标通知。历史索引语法、不同设备初始化配置布局、其他用例迁移留到需要时确定。

本次实现范围是 presence 用例及其数据准备、设备组合、通用引用、事件匹配和取证链路。没有修改 SDK、原生桥接、example 人工入口或 CI；单设备旧直跑仍保留。
