# 用例执行与故障排查

目标：执行用例，按故障归属完成排查、修复和复验。

## 执行闭环

执行中出现的故障按以下流程处理，直到本轮完成：

执行 → 发现问题 → 复验与排查 → 按职责修复 → 复验 → 继续执行。

## 规则与边界

1. 执行阶段负责发现问题、记录证据、初步归因和分流，并协调对应模块完成修复与复验。
2. 用例设计问题通过修正用例解决；SDK、设备、环境、数据准备等问题由对应模块负责修复。各类故障均纳入执行闭环，按问题归属划分修复职责。
3. 正式执行失败须复验，由 AI／人工检查证据后显式发起；需要恢复前置状态时先 `prepare`，再 `launch/run`，执行时明确启动记录。尚未复验标为“待复验”；开发、调试阶段不强制。
4. 影响后续用例时暂停受影响的执行，故障修复并复验通过后继续；不受影响的用例继续执行。
5. 修正用例须遵守已确认的场景和预期，不得为绕过 SDK 问题修改正确用例或降低断言要求；各类修复涉及重大变更时，均遵循 [spec.md](../spec.md) 的确认规则。
6. 暂时无法修复或需要用户决策的问题，保留证据并明确失败或阻塞原因，不无限重跑；本轮完成不等于全部用例通过。
7. 模块交接不合格时立即停止依赖操作，记录生产方、接收方、来源操作、预期、实际及证据。输出违约修上游，验收误判修接收方，错传输入修编排；外部状态变化单独查证。返工后重验受影响产物，不转移职责、放宽检查或自动重放命令，契约见[执行规格 §1.4](../../docs/spec/2026-11-06-testing-v2-spec.md#14-交付格式与接收验收)。

## 故障沉淀

- 每次解决故障后，将现象、已确认根因、修复方法和验证结果记录到 [troubleshooting/](../troubleshooting/)，纳入 Git 长期保存。
- 一问题一文档，命名为 `YYYY-MM-DD-<问题主题>.md`；已有同类记录时更新原文，避免重复。
- 记录关联测试轮次及必要证据位置，并说明适用条件，便于再次遇到问题时查找和复用。

## 轮次与产物命名

- 每次启动一轮执行，生成独立 `runId`：`YYYYMMDD-HHmmss-<场景>-<短随机后缀>`，例如 `20261106-152800-presence-a3f9`；时间使用宿主本地时间。
- 同一轮临时数据和日志放在 `tmp/<runId>/`，报告放在 `reports/<runId>/`；文件名按内容命名，不重复添加时间戳。
- 轮内复验保留在同一轮中，用例标识与执行序号区分各次记录，不覆盖首次失败。重新完整执行则创建新一轮。
- 不设置专门的开发、调试或正式执行模式；每轮独立保存结果。需要正式结果时重新完整执行一轮，不混入其他轮次的数据。
