# 多设备协同测试执行流程

目标：完成多设备协同系统测试。

[编写用例](2026-11-06-test-case-authoring.md)属于执行前的准备工作。用例完成并验证通过后可重复执行，无需每轮重新编写。

[数据准备](2026-11-06-data-preparation.md)中的账号源码由辅助脚本在 Dart CLI 启动前生成；用例业务前置状态由 CLI 的数据模块按已确认声明准备并核验。

## 执行流程

1. [设备准备](2026-11-06-device-preparation.md)
2. 编译被测应用
3. 安装运行
4. [执行用例](2026-11-06-test-execution-troubleshooting.md)
5. [汇报总结](2026-11-06-reporting.md)
6. [必要清理](2026-11-06-cleanup.md)

设备及构建可在本轮内复用。每个用例开始前，按需准备并核验其业务前置状态，再安装运行和执行用例，不能提前批量准备互相冲突的状态。

## 执行入口与编排

1. 由 Dart `main` 提供分环节操作和全流程自动化；分环节用于排查、调试及正式失败后的显式复验，全流程用于一次组织完整轮次，两种方式复用同一套模块实现。
2. Dart 编排层负责执行顺序、本轮数据传递、失败时继续或暂停，以及报告和收尾；具体操作由各模块负责。
3. 全流程共用 `runId`；分环节消费已有输入时须指定轮次，纯设备或构建操作也创建独立运行标识并保留日志、产物，不要求账号和用例数据。
4. 宿主命令由 Dart 调用；`tool/flow_runner` 负责用例内部控制流，Dart 编排层负责整个测试任务的生命周期。

## 环节连接

1. 各环节明确输入、产物和完成条件，返回执行状态、产物、错误及证据位置；编排层负责交接和后续执行判断。
2. 同一进程通过内存中的运行上下文传递数据。在阶段开始、结束或失败时，将阶段状态和产物引用保存到 `tmp/<runId>/`，供排查及分环节调用恢复；详细过程保留在日志中。
3. 各模块只接收所需输入并返回自身结果，运行上下文及其快照由编排层统一维护。
4. 后续执行取决于所需输入和前置条件，不统一要求上一环节成功：准备失败阻断依赖它的用例，用例失败仍需汇报，清理遵守产物保护规则。
5. 区分环节完成与测试通过。产物能证明本次环节结束，测试结论由产物内的实际结果及断言决定。
6. 分环节恢复时重新检查设备、App 等外部状态；不得仅凭快照判断就绪或盲目重发已执行的业务命令。

## 日志规则

目的：快速定位问题。以下规则适用于全部执行阶段。

1. 日志应能定位时间、测试轮次、阶段和步骤；涉及设备时标明设备。
2. 记录阶段执行及模块调用的开始、结束、必要输入和关键结果，能够判断流程停在哪里。
3. 调用宿主命令时保留标准输出、错误输出及退出状态；失败时保留原始错误和调用上下文，不能只有“执行失败”。
4. 工具日志与被测应用日志应能按测试轮次和设备关联；报告提供对应日志和证据的位置。
5. 日志中的敏感数据须脱敏，不输出 Token、密码、密钥等敏感值。
