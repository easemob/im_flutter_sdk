# 联系人多端用例结果不稳定：事件归属与延后投递排查

日期：2026-11-05。关联：[双 iOS 三轮验证过程](2026-11-05-dual-ios-contact-add-verification.md)。

## 1. 结论与尚未定位的边界

三轮不同结果不是一个随机网络错误的三种表现，而是**真实的通知延后投递与测试缺少事件归属约束叠加**。

| 现象 | 本次定位结果 |
|---|---|
| 第一轮 9 passed / 1 failed | 已确认匹配旧接受通知，提前查询好友列表。匹配通知在服务端的生成时间为 18:11:43，本轮真实接受发生在 19:19:42。 |
| 第二轮 5 passed / 2 timeout | 已确认本轮邀请生成，但没有在本轮原生收包日志中出现；同一消息在第三轮登录时才收到。具体为何未及时投递，尚未定位到服务端或传输层内部原因。 |
| 第三轮 10 passed | 已确认 Bob 匹配第二轮遗留邀请并据此调用接受；当前邀请通知稍后才到。这是受旧通知污染的通过，不能作为本轮完整因果链的成功证据。 |

**tool/flow_runner 存在本场景下的验证缺口：只有进程事件游标，没有业务运行关联边界。** 它按现有 `source + userId` 条件接受了真实但属于历史操作的事件。`runId` 只是报告标识，未给 SDK 回调提供本轮身份。

本次没有发现当前用例的 parallel/barrier 提前放行、命令重复下发或 HTTP 返回结果串设备。此结论只覆盖本次路径，不能推导为整个解释器已无其他缺陷。第二轮原生收包前的投递异常也不能归责于解释器。

## 2. 原始三轮的完整证据链

### 第一轮：用 68 分钟前的接受通知放行了查询

从模拟器 App 数据容器提取两类日志：

- `Documents/api_test.log`：完整 Dart 结构化日志，带 `ts` 和 `seq`，避免 os_log 采集不完整的问题。
- `Library/Application Support/HyphenateSDK/easemobLog/easemob.log`：原生收发协议及 SDK 日志，ROSTER 元消息带生成时间、消息 ID 和操作类型。

| 时间（设备本地时间） | 证据 |
|---|---|
| 19:19:42.116 | Alice 原生收到一批历史 ROSTER，首条 REMOTE_ACCEPT 的 metaId 为 `1616233573524701596`，消息生成时间为 18:11:43.224；还包含 18:18、18:43、18:51、18:55 等历史操作。 |
| 19:19:42.123 | Dart 将首条接受通知记录为 seq=21，运行器 `wait_event` 匹配了它。 |
| 19:19:42.127 | 历史批次中的删除操作已经传播到 Dart，seq=34 为 onContactDeleted。 |
| 19:19:42.242 | Bob 才开始执行本轮 acceptInvitation。 |
| 19:19:42.306–.308 | Alice 查询本地好友列表，结果 `[]`。 |
| 19:19:42.311 | Bob 本轮 acceptInvitation 成功返回。 |
| 19:19:42.358–.361 | Alice 收到本轮 REMOTE_ACCEPT，生成 Dart seq=40/41（接受、添加）；运行器之前已完成错误的等待与查询。 |

因此，空列表不能解释成“真实接受通知之后 SDK 未入库”：用例在**旧接受通知之后、本轮接受完成之前**进行了查询。旧事件到达时间晚于运行器启动游标，所以未被游标过滤。

### 第二轮：邀请确实生成，通知延后到下一轮

- Alice 原生 `inviteContact()` 于 19:21:23.169 调用，REST `contacts/apply` 成功，返回 `applyContacts: [zuoyu02]`。
- Bob 已有 onConnected、同步事件及 REMOVE 通知；在等待窗口内没有 ADD/邀请的原生收包记录，Dart 和 HTTP 事件也没有邀请。没有证据支持“HTTP 缓冲有事件但解释器漏匹配”。
- 两个等待在 20 秒超时，接受及后续查询没有执行。Alice 等不到接受是 Bob 未接受的下游结果。
- 后续 REST 查询双方好友列表为空，说明结束时关系非好友，但并不说明邀请队列为空。
- 第三轮 Bob 在 19:23:13.428 收到下列原生消息：

```text
metaId          = 1616251526999703972
namespace       = ROSTER
operation       = ADD
messageTimestamp= 1793877683346（2026-11-05 19:21:23.346）
reason          = contact-add-positive flow
```

该时间戳属于第二轮，不是第三轮发送时间。原生数据表明消息没有凭空消失，而是滞留后随下一次登录同步到达。

**已定位边界：通知投递到 Bob 原生协议处理之前。尚未定位：服务端在线路由、队列通知、连接状态或传输处理中的具体故障点。** 本机日志没有服务端发送尝试、路由选择及确认记录，不能进一步断言是某一方的实现缺陷。也不能用“等待同步完成”当作已证实修复：第二轮 Bob 的离线消息同步结束在 19:21:23.138，早于 Alice 调用发送的 19:21:23.169。

服务端后续排查可用上述 metaId、测试账号 zuoyu01→zuoyu02、19:21:23 至 19:23:13 的窗口定位。查清消息是否实时路由、路由到哪个连接、是否发过 NOTICE/SYNC、为何要下一次登录才拉到。跨端及服务端时钟可能有偏差，不用几十毫秒的跨时钟差计算精确延迟。

### 第三轮：当前邀请尚未发出，等待已经拿到旧邀请

| 时间（同一宿主上的模拟器本地记录） | 证据 |
|---|---|
| 19:23:13.428–.429 | Bob 收到上面的旧 ADD，记录为 seq=15，运行器匹配此条。 |
| 19:23:13.453–.455 | Alice 才开始本轮 addContact。 |
| 19:23:13.463 | Bob 根据 seq=15 开始 acceptInvitation。 |
| 19:23:15.791–.793 | Bob 收到本轮新 ADD，metaId=`1616252010032529828`，生成时间 19:23:15.822，Dart seq=19。 |

两条邀请有不同原生消息 ID 和生成时间，已排除“同一条本轮邀请重复记录”的解释。前次记录中关于两条来源不明的保留意见，至此已收敛为“上一轮邀请 + 本轮邀请”。

双方最终好友列表正确，所以原断言会全绿，但它没有证明当前发送导致了当前接收和接受。

## 3. 为什么现有运行器挡不住

涉及 [interp.dart](../../tool/flow_runner/lib/interp.dart)、[http_agent_client.dart](../../tool/flow_runner/lib/http_agent_client.dart)、[agent_client.dart](../../tool/flow_runner/lib/agent_client.dart)。

1. `Interpreter.run()` 在 init/login 前执行 `_initEventCursors()`，只记录此时已进入 App 的事件末尾。新 App 的末尾通常为 0。
2. 登录后到达的历史服务器通知获得全新的 App seq，满足 `seq > 起始游标`，即使业务发生在上一小时也会进入候选集合。
3. `_waitEvent()` 只比较事件 source 和 YAML 的 match。此用例两处只匹配 peer userId；同一账号历史事件也符合条件。
4. 匹配成功即结束等待并推进下一个命令，没有检查通知是否由本轮操作产生。新 commandId 仅标识 HTTP 命令，也无法自动关联 SDK 通知。
5. HTTP 事件只提供 `seq/source/payload`，不含原生元消息 ID、生成时间；命令结果转为 Envelope 时也没有保留 `commandId/evidence`。这些信息缺失增加诊断难度，不能靠报告 runId 自动补出因果关系。

这同时涉及执行工具和用例契约：工具未提供表达足够关联边界的能力，用例/前置又把“非好友 + 登录命令完成”当成“可开始一个没有历史通知的测试”。REST 只重置关系，不重置通知队列；屏障只等待命令结果，不等价于已排空全部历史事件。

简单把游标移到“发送命令完成之后”也不正确：对端回调可以先于发送接口返回，可能反而丢掉本轮合法事件。第一轮的历史通知甚至在发送开始之后才到，仅增加时间下界也不够。

## 4. 定向实验：从随机现象变为可重复的证据

### 无网络的真实解释器实验

临时脚本 `testing/tmp/contact-ios-investigation/replay.dart` 直接导入真实 Interpreter/Parser，加载原 YAML 和两个原 JSON 命令库；仅用内存 AgentClient 控制输入事件和接口结果，不修改解释器。

| 输入情形 | 次数 | 每次结果 | 证明的内容 |
|---|---:|---|---|
| 没有历史事件，当前邀请及接受正常产生 | 10 | 10 passed | 基本流程可正常执行。 |
| 登录阶段注入旧接受通知；本轮真实接受在查询之后完成 | 10 | 9 passed / 1 failed | 不依赖网络即可稳定复现第一轮的提前查询。 |
| 登录阶段注入旧邀请；完全不投递本轮新邀请，接受旧邀请后关系建立 | 10 | 10 passed | 本轮邀请通知缺失也可全绿，验证缺口确定存在。旧邀请 reason 特意设为 previous-run，仍会通过 userId 匹配。 |
| 没有历史邀请，也不投递本轮新邀请 | 1 | 5 passed / 2 timeout | 当前等待路径在确实无事件时正确超时，没有凭空合成回调。 |

这是故障注入实验，说明工具面对特定输入会怎样，不是对真实 SDK 行为的模拟验收，也不计入设备通过率。

### 带日志的设备对照

在 `testing/tmp/contact-ios-investigation/trace_runner.dart` 复制 CLI 入口，以 HttpAgentClient 子类记录发送、完成、事件轮询游标和事件 seq。仍使用原解释器、原 YAML、原命令库及原构建，不改执行断言。

- 运行目录 `testing/tmp/contact-ios-diag1` 至 `contact-ios-diag5`：5 次均 10 passed。
- 日志显示 addContact 在两端 login 返回之后下发，没有当前屏障提前放行；每端原有命令均只下发一次。
- 第 2–5 次诊断副本在流程结束后暂不调用 finish，以便保留失败现场供补充查询；此差异发生在测试步骤完成之后。诊断结束另行关闭。
- 本次未再次复现第二轮的底层延后投递。额外日志也可能扰动时序，5 次成功不能排除低概率竞态，更不能证明 99% 稳定。

## 5. 后续处理建议（未实施）

1. **先修正测试的事件归属契约。** 需要明确触发前准备、事件观察边界、旧事件处理和失败报告；能携带唯一标识的邀请可用 reason 关联。接受通知只有 userId，需结合账号隔离或已验证的历史事件处理办法，不能假装它带有 runId。
2. **把“关系前置”与“历史通知隔离”分开验收。** 新进程、REST 删除关系、新报告 ID 都不等于清空旧业务事件。测试账号共享时还应避免其他任务并发修改关系。
3. **保留底层延后投递为独立问题。** 按 metaId 查服务端/传输链路，不以加大超时、固定 sleep 或不停重跑来掩盖。真实 SDK/服务端失败应继续如实报告。
4. **将上述定向输入纳入修复后的回归验证。** 先确保不会假通过，再谈通过率。若以“独立、同分布运行，单侧 95% 置信下界≥99%”作统计目标，需要约 299 次零失败；这一计算仍不能替代状态隔离和因果验证，也不是本次已经完成的验收。

本次只做读取、诊断辅助和文档沉淀，没有实施以上修复。
