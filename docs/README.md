# 文档目录说明

这个目录用于沉淀项目讨论、设计、计划和后续演进文档。为了后续沟通顺畅，文档按类型放置，不把不同阶段的内容混在一起。

这不仅仅是设计文档，更是项目的核心和灵魂。

```
想法 -> 调研 -> 取舍 -> 设计 -> 规格 -> 计划 -> 实现 -> 验证
```

已确认值得处理但尚未排期的事项进入 `backlog/`；正式排期后再编写 `plan/` 实施计划。

## 目录约定

```text
docs/
├── README.md
├── PROGRESS.md
├── backlog/
├── drafts/
├── research/
├── decisions/
├── spec/
├── plan/
├── testing/
├── design/
├── refs/
│   └── troubleshooting/
└── workflow/
```

**子文件夹规则（强制）**：`backlog/`、`drafts/`、`research/`、`decisions/`、`spec/`、`plan/`、`design/`、`refs/` 下的所有文档都必须放在子文件夹中，不允许直接放在这些目录的顶层。`workflow/` 文档数量少，暂不强制子文件夹，直接放顶层即可。子文件夹由文档创建者根据实际内容自行命名（主题名，不加日期前缀；日期前缀规则仍作用于文件夹内的文档文件名）。2026-09-22 之前已存在的不符合该规则的文档暂时保留原位，不做迁移；新增文档必须遵守。

## PROGRESS.md

`PROGRESS.md` 是一句话一项、带完成状态的 roadmap。

当前测试说明见 [测试指南](testing/README.md)，本轮目录整理验证见 [5.1.0 验证记录](porting/5.1.0/2026-11-09-testing-directory-verification.md)。

## backlog

`backlog/` 放已经确认值得处理、边界基本明确，但尚未排期的工作项。

适合放：

- 已确认的技术债和流程改进
- 暂不进入当前迭代的缺陷修复
- 已有事实依据、等待后续安排的工程任务
- 需要保留背景、证据、任务拆分和验收标准的待办

backlog 文档不是开放式想法，也不是实施计划。内容应说明问题为什么成立、准备解决什么、明确不做什么以及完成判据。正式排期后，应另建 `plan/` 文档，并在原 backlog 文档中补充计划链接和状态。

## drafts

`drafts/` 放探索类、讨论类、未定稿文档。

适合放：

- 原始想法
- 方案探索
- 技术路线比较
- 调研前的问题和假设
- 还没有形成明确结论的讨论材料

这类文档允许保留不同观点和未收敛内容，但不记录讨论流水账。等内容稳定后，再整理到 `backlog/`、`research/`、`decisions/`、`spec/`、`plan/` 或 `design/`。

## research

`research/` 放事实性调研资料。

适合放：

- 外部资料整理
- API、协议、平台能力调研
- 竞品或同类方案分析
- 技术约束确认
- 链接、出处和结论摘录

这类文档重点记录“资料确认了什么”，尽量区分事实、推断和个人判断。它可以支撑 `drafts/` 里的方案讨论，也可以支撑后续 `decisions/` 的决策记录。

## decisions

`decisions/` 放关键决策记录。

适合放：

- 已经确定的技术路线选择
- 重要方案取舍
- 不采用某个方案的原因
- 阶段性架构决策
- 会影响后续实现和维护的约束

决策文档应该说明背景、候选方案、最终选择、选择理由和影响。它不追求长，但要能让后续读者理解“当时为什么这么决定”。

## spec

`spec/` 放规格文档，也就是已经收敛后的需求、边界和行为定义。

适合放：

- 功能规格
- 模块规格
- 输入输出约定
- 业务规则
- 验收标准

规格文档应该尽量清晰、可执行，减少开放式讨论。

## plan

`plan/` 放实现计划文档。

适合放：

- 分阶段实施计划
- 任务拆解
- 里程碑
- 测试计划
- 发布或迁移步骤

计划文档应该服务于执行，重点说明先做什么、后做什么、每一步如何验证。

## design

`design/` 放总体设计、架构设计和路线图类文档。

适合放：

- 总体架构
- 系统边界
- 数据流
- 组件关系
- 长期路线图
- 未来演进方向

设计文档用于沉淀相对长期的判断，不放太细的单次实现任务。

## refs

`refs/` 放参考类文档，即完成某件事之后沉淀下来、供日后查阅的资料。

适合放：

- 部署、运维等操作指南
- 协议、数据格式说明
- 排查手册、FAQ

`refs/` 与上面各目录的区别：那些目录对应文档的生命周期阶段（想法到设计），内容随阶段推进而流动；`refs/` 不按阶段划分，放的是已经稳定、长期有效的"成品资料"，供需要时直接查阅。

### 常见问题与排查（refs/troubleshooting）

`refs/troubleshooting/` 统一收录常见故障、容易误判的报错、配置陷阱和使用误区的分析与排查结论。已有排查文档保留原位，新增此类文档放入该目录。

- 一问题一文件，文件名使用 `YYYY-MM-DD-问题主题.md`，例如 `2026-11-04-vscode-swift-flutterframework-missing.md`。
- 内容保持简短，记录现象、适用环境、结论与证据、影响范围、处理建议和验证状态。
- 明确区分已确认原因、尚未确认部分、未实施或未验证的建议；未修复的问题也可沉淀已确认的事实，不将推测写成结论。
- 如需安排后续修复，另建 `backlog/` 或 `plan/` 文档并相互引用。

## testing

`testing/` 放当前测试体系的分类、设计原则、执行入口和结果判定规则。入口见 [测试指南](testing/README.md)，按 CI、单设备平版、多设备平版分别维护；工具的详细参数留在工具目录，版本验收证据放在 `porting/<版本>/`。

## workflow

固定的重复的工作流程放在这里。

## 平版产物（docs/porting/）

本仓库 SDK 版本平版的阶段产物放在 `docs/porting/<目标版本>/`：`01-api-diff.md`、`02-contract.md`、`03-implementation.md`、`04-verification.md`、`acceptance-report.md`。`PROGRESS.md` 登记进度；`research/` 中更早的平版文档属历史留档，不迁移。

## superpowers 文档

如果后续使用 superpowers skill 生成自己的规范、计划或记录，它会有自己的目录和格式约定。这部分不纳入当前目录规则，也不需要手动调整。

## 使用原则

- 由 agent 创建或整理沉淀的项目文档，需要加上当天日期为文档名字前缀。例如：`2026-07-09-`。
- 用户自己的手写草稿不受日期前缀规则约束；如果需要调整，由用户自行处理。
- 先探索，放 `drafts/`。
- 问题已经确认但尚未排期，放 `backlog/`。
- 查资料、确认事实，放 `research/`。
- 做出关键取舍，放 `decisions/`。
- 收敛成需求或行为定义后，放 `spec/`。
- 准备执行时，放 `plan/`。
- 涉及长期结构、架构和路线图时，放 `design/`。
- 操作指南、格式说明等长期查阅资料，放 `refs/`。
- 固定的重复的工作流程，放 `workflow/`。
- 不确定该放哪里时，先放 `drafts/`，后续再整理。

## 收敛原则

- 文档记录稳定内容，不记录中间过程。
- 已经废弃的临时工具、方案或尝试，不需要为了说明过程而写入文档。
- 如果一个内容只是讨论中短暂出现，且没有形成结论、事实或决策，默认不沉淀。
- 当文档开始变长时，优先拆分、归档或提炼结论，而不是继续追加。
