## 1. 目标与范围

以数据准备工具、日志读取工具和预定义脚本支撑 AI 执行测试，先按规格与脚本完成真实执行，第四阶段再将成熟流程写入新的测试 skill（名称待定），供后续版本升级使用。主代理依据主脚本编排，设备子代理依据子脚本操作，各阶段以日志和断言作为推进依据。

example 同时服务人工和 AI。改造必须保证人工能够正常初始化、登录、查找并调用 API、查看返回值及事件，方便用户亲自抽验。AI 能力的增加不得使人工操作依赖主代理、子代理或自动化脚本。

本次包括单设备正向／逆向测试、多设备交互测试、工具与脚本的集中组织、制作规范及 skill。接受新旧脚本格式和路径不兼容，但旧内容清理按第三阶段单独决策。当前不改造 `flutter2_stable`，不安排全仓库测试框架迁移。

### 1.1 平版与运行验证的交接

`platform-sdk-porting-v2` 负责平版实现、契约检查、静态检查和编译验证；新的测试 skill 负责测试用例编写与设备上的真实运行验证。前者现有可选功能验证不替代后者的完整验证，本次不修改外部平版 skill。

新的测试流程读取 `docs/porting/<版本>/` 的 API diff、契约、实现记录、验证记录和验收报告，对照当前代码建立“变更项 → 用例 → 实际结果”映射。未确定语义单列，不猜预期，也不阻塞其他明确用例。允许小幅补齐 example 的 API 注册、参数模板和日志展示并验证受影响部分；SDK 业务缺陷保持证据，修复另行决定。第一轮按文档执行，不能依赖尚未编写的 skill。

## 2. 当前基础与缺口

以下为源码检查结果，未在本次规格编写期间执行设备测试：

| 内容 | 当前基础 | 本次需要补齐 |
|---|---|---|

| 单设备脚本 | 顺序执行、配置／步骤结果引用、超时及错误码断言 | 数据与状态断言、格式校验、明确的阶段和失败语义 |
| 事件与日志 | 监听事件输出到结构化日志 | 按运行／设备读取，等待事件，关联操作与断言 |
| 多设备 | 可复用设备启动和脚本投递能力 | 主／子脚本、阶段协调、设备会话保持和结果汇总 |
| 人工模式 | 初始化、登录、API 搜索与调用、浮动日志 | 保持可用，并覆盖本次纳入测试的 SDK API |

现有自动模式启动时只读一次脚本，自动初始化和登录；初始化后、登录前已注册监听，但没有等待主代理放行登录的控制点。现有报告工具在收到 `script.done` 后约两秒向 `flutter run` 发 SIGINT；不能据此推断所有设备上 App 的最终进程状态，但现有 runner 确实不提供持续阶段会话。需区分阶段完成和场景结束，保留既有执行器并补充阶段控制。

依据：[`auto_mode.dart`](../../im_flutter_sdk/example/lib/auto/auto_mode.dart)、[`step_expectation.dart`](../../im_flutter_sdk/example/lib/auto/step_expectation.dart)、[`listeners.dart`](../../im_flutter_sdk/example/lib/listeners.dart)、[`auto_report.dart`](../../tool/auto_report.dart)、[Makefile](../../Makefile)。这些是评审时的现有路径，迁移实施时同步调整引用。

### 2.1 复用原则

现有工具是不够完善，而非不可用。新目录组织不构成重写理由：优先复用现有实现，再调整路径、参数与输出，最后仅对缺失能力增加实现。保留已有回归测试及曾修复的问题，如 Android `run-as` 投递、长日志分片重组和凭据处理。确需替换某部分时，在实施记录中说明现有实现的限制与验证依据。

数据准备继续复用 `env_tool.dart` 的配置／Token 链路与 `rest_resource_client.dart` 的资源操作；执行和报告复用 `auto_report.dart`；App 内继续复用 API 注册、监听、日志和自动模式。不得为统一目录另建一套相同业务逻辑。迁移与第三阶段清理分开，旧入口有依赖时可暂时保留转发。

## 3. 职责与执行关系

| 组成 | 职责 |
|---|---|
| 数据准备工具 | 准备或检查账号、Token、群等前置数据，输出可引用的资源；支持本次创建资源的清理 |
| 日志读取工具 | 读取本次运行指定设备的 API 结果和回调，提供增量读取、过滤和有超时的等待，保留判定证据 |
| 单设备脚本／设备子脚本 | 定义本设备操作、断言、等待条件、阶段输出和清理动作 |
| 主脚本／主代理 | 定义角色和依赖顺序，绑定设备，分派阶段，接收证据，向下一阶段传递数据并汇总 |
| 设备子代理 | 一个子脚本对应一个子代理和一台设备；执行本设备任务并汇报，保持必要的 App 会话 |
| skill | 根据 API 变化和契约指导脚本生成、工具复用、校验、执行、证据审查与结果归档 |

子代理的协调统一经过主代理。主代理解释主脚本并派发阶段；子代理绑定设备，通过工具执行本设备阶段内的步骤，完成后保持 App 会话等待下一阶段。AI 按预定义流程执行，不临时改动预期来迎合实际返回。

采用“子代理主动回报 + 主代理读取日志核验”：回报用于通知进度，结构化执行日志和断言证据用于最终判定；主代理不能只相信聊天中的“完成”。每条命令有运行、命令、角色、阶段标识与输入及超时；接收确认不等于执行成功；结果必须带输出和证据范围。同命令 ID 不重复执行，相同 ID 不同内容拒绝；超时或中断后执行状态不明时先核查，禁止盲目重发。详见协同协议与样例。

## 4. 目录与产物

本规格存放于 `docs/spec/`，由测试入口链接。测试体系目标结构如下；仅随实际实现创建所需内容，不提前建立空工具框架。

```text
testing/
├── README.md
├── spec/                       # 脚本格式与执行规则
├── skills/
│   └── <name>/SKILL.md          # 名称待定，第四阶段编写
├── tools/
│   ├── data/                   # 数据准备与清理
│   ├── logs/                   # 日志读取与事件定位
│   ├── runner/                 # 执行支持与报告
│   └── validate/               # 格式、引用、能力检查
├── config/
│   ├── environment.example.json
│   └── environment.local.json  # 本地配置，Git 忽略
├── scripts/
│   └── 5.0.0/
│       ├── single/
│       └── multi/
│           └── data-sync/      # 同一场景的主脚本与设备子脚本
├── tmp/<run-id>/               # Git 忽略；main/、device1/、device2/ 等
└── reports/<run-id>/           # Git 忽略；最终结果及必要证据
```

- 测试资料和宿主机工具集中于 `testing/`。Makefile 可保留快捷入口，具体路径随实施更新。
- 依赖 Flutter 和 App 生命周期的执行、监听代码保留在 example 内；人工／AI 共用的 API 注册、调用和日志能力保持单一实现，从统一入口可以定位。
- skill 正文只维护一份；名称和接入 AI 工具的发现方式在第四阶段确定，本轮不创建 skill。
- `tmp/` 接收运行中生成的脚本副本、中间结果、临时日志和协调文件；不同运行及设备相互隔离。运行中的目录不得被清理。
- 运行结束后可删除整个 `tmp/<run-id>/`。必要证据须先归档至 `reports/<run-id>/`，报告不得依赖临时文件。
- 本地长期配置不随临时目录清理；凭据和 Token 不进入版本化脚本或归档报告。配置模板不含真实凭据。
- 设备内文件、Flutter 要求的生成文件与构建缓存遵守各自平台位置；宿主机收集的测试中间产物统一进入 `tmp/`。清理测试临时目录不删除人工使用的数据。

## 5. 脚本分类与命名

预期行为分为 `positive`、`negative`；执行方式分为 `single`、`multi`。交互用例同样可以是正向或逆向。

```text
<version>-single-<feature>-<positive|negative>.json
<version>-multi-<feature>-<positive|negative>-main.json
<version>-multi-<feature>-<positive|negative>-device<N>.json
```

示例：

```text
5.0.0-single-message-edit-positive.json
5.0.0-single-message-edit-negative.json
5.0.0-multi-data-sync-positive-main.json
5.0.0-multi-data-sync-positive-device1.json
5.0.0-multi-data-sync-positive-device2.json
```

- 固定使用 `multi`，不使用 `multi2` 等数量后缀。主脚本列明所需设备角色，设备数量从角色定义得出。
- `device<N>` 是逻辑设备角色；执行时绑定实际设备 ID。同一账号可用于多个角色，账号和设备不是同一概念。
- `feature` 描述可辨认的功能／场景；同功能的不同场景用更具体的名称区分。
- 版本表示用例引入或行为变更版本；后续版本可复用未变化的用例，不整套复制。实际运行版本、平台和提交记录在报告中。

## 6. 脚本规范要求

脚本采用 JSON，供 AI 和工具共同读取。第一阶段交付独立的格式说明、机器可执行的校验规则及示例。本规格定义必要语义；具体字段名、协调传输机制和工具命令参数在实施设计中收敛。

每个用例必须能明确表达：

| 信息 | 要求 |
|---|---|
| 身份与目的 | 唯一用例标识、版本、功能、正向／逆向、单／多设备、适用平台 |
| 前置条件 | 账号关系、设备角色、服务能力、初始登录／数据状态、所需资源及准备方法 |
| 操作 | 唯一步骤标识、SDK API 与参数，或执行支持操作；顺序和依赖明确 |
| 引用与输出 | 配置、前序结果和跨设备阶段输出使用明确引用，不在脚本中写死运行产生的 ID |
| 预期 | 返回值、错误码、数据状态、事件及必要的顺序约束；写明预期依据 |
| 等待与失败 | 超时、依赖失败处理、是否允许重试及理由；不以固定睡眠代替就绪证据 |
| 清理 | 本次资源归属、结束／失败时清理动作及清理失败记录 |

执行前拒绝未知操作／断言字段、重复 ID、未定义引用、不合法角色绑定及循环依赖。运行时无法解析的引用应明确失败或阻塞，不能悄悄替换成空值继续调用 SDK。

正向测试除调用成功外，应检查可观察的业务结果，如未读数归零、消息内容和 attributes 更新。逆向测试应构造可控前置条件并检查约定错误，必要时验证原状态未变；不强行为所有 API 制造反例。超时、脚本错误、未注册 API 或崩溃不能作为“预期失败”通过。

## 7. 日志、事件与阶段协调

日志读取结果应能关联运行、设备、步骤／阶段、事件来源、设备内序号及业务标识。工具可以在采集层补充运行上下文，不要求 SDK 回调携带全部字段。

- AI 能查询从指定观察位置之后新增的日志，区分尚未出现、匹配成功、超时和日志读取故障。
- 先建立接收端监听和观察起点，再触发操作；随后等待时仍能匹配观察起点之后已经到达的事件，避免丢失快速回调。
- 按账号、消息 ID、群 ID、同步类型等场景相关信息过滤；不将历史或无关事件算作通过证据。
- 设备内顺序使用事件序号等证据；跨设备顺序依据主代理的阶段依赖和确认，不能只比较设备时钟。
- 子代理完成当前阶段后汇报结果及必要输出，App 按需要保持在线；只有场景结束或明确终止时才结束参与。
- 初始化、登录或准备阶段失败，依赖步骤标记阻塞。超时调用可能仍在底层运行，后续依赖阶段不得直接按成功推进。
- 重试不得隐式重复产生有副作用的操作，也不能掩盖测试本来要观察的错误。

交互场景按单聊回执 → 群聊回执 → 同账号数据同步的顺序落地，先用触发关系明确的单聊回执验证协作机制。数据同步场景流程为：准备数据 → A 登录并形成可验证数据 → B 初始化并确认监听就绪 → 主代理允许 B 登录 → B 检查规定的同步事件及实际数据 → 主代理汇总和清理。

同步 options 的 mask 已有契约：conversations=1、contacts=2、joinedGroups=4，且双端默认值不同，脚本必须显式设置本场景所需值。具体选哪类数据、如何形成可同步服务端数据及排除 B 缓存残留，需要在实施前核实。编写此用例时需核实同步事件类型、配置要求、登录策略和触发条件；`onDataSyncStart/onDataSyncFinish` 与多设备事件分别按各自契约验证。不直接假定“同账号第二台设备登录必然触发所有同步事件”。

### 7.1 第一阶段用例内容

单设备用例以现有 [`script_500_apis_positive.json`](../../im_flutter_sdk/example/scripts/script_500_apis_positive.json) 的 20 个步骤和 [`script_500_apis_negative.json`](../../im_flutter_sdk/example/scripts/script_500_apis_negative.json) 的 10 个步骤为内容基线。按功能组织新文件，保留原步骤到新用例的覆盖映射；步骤数不是最终用例数，准备和清理步骤可复用。

- 正向保留未读数查询／清理、消息编辑含 attributes、群配置创建／更新、回执、本地及服务端查询、混合有效／无效消息批次、设备管理和 Token 更新，增加可验证的业务结果断言。
- 逆向保留非法群成员／缺失群 600、缺失修改消息 500、空会话及无有效消息回执批次 110、设备管理无效 Token 303、空 Token 更新 104。错误码来自现有脚本及历史记录，实际执行仍核对当前契约和平台表现，不默认为本次已通过。
- `fetchGroupMessageReadReceipts` 缺失消息的已知 Android native 崩溃继续屏蔽并报告，不能在迁移时无意重新启用；混合批次按现有 native 语义处理，不在 Flutter 构造替代错误码。

多设备选取以下三个典型场景，内容依据 [5.0.0 契约](../porting/5.0.0/02-contract.md)、[验证记录](../porting/5.0.0/04-verification.md) 和 [验收报告](../porting/5.0.0/acceptance-report.md)，不把历史单设备通过结论当作多设备已验证：

| 场景 | 设备／账号关系 | 主要操作与断言 |
|---|---|---|
| `data-sync` | 两设备、同账号 | A 准备可同步数据，B 建立监听后登录；检查契约规定的同步开始／结束、错误状态及实际同步数据，数据库打开事件按其触发契约检查 |
| `direct-read-receipt` | 两设备、两账号 | A 发单聊消息，B 确认接收后发送已读回执；A 检查 `onMessageReadReceipts` 中本次消息、会话及单聊回执状态 |
| `group-read-receipt` | 两设备、两账号、同一临时群 | A 发送需回执群消息，B 接收并发送回执；A 检查回调、本地汇总和服务端非空详情中的消息／成员信息；尊重 `totalCount` 平台差异 |

三个场景先实现正向闭环，逆向场景按已核实的可控契约补充，不为数量强造。历史文档“暂不测试双账号”的决定属于当时平版范围，本次多设备需求补齐该覆盖。群回执场景复用 REST 群准备与清理能力，SDK 回执操作仍由设备执行。

## 8. 数据准备、结果与后续 skill

数据工具按需复用和更新：脚本声明资源需求，工具准备或检查后返回结构化引用；账号、Token、群及其他资源能力不足时才扩充工具。区分复用资源与本次创建资源，清理仅处理本次拥有的资源。环境能力不满足时给出阻塞原因，不把它算作成功。

结果至少区分通过、失败、阻塞、跳过。仅在所有必需断言完成且通过时报告场景通过；无法运行、无有效步骤、事件证据缺失或存在必需阻塞项时不得报告通过。已知问题跳过需保留理由和覆盖缺口。清理结果单独记录，不能覆盖原始失败。

最终报告保留脚本版本／标识、代码提交、运行平台与设备角色、阶段／步骤结果、预期和实际值、必要事件证据、未完成项及清理状态。AI 的解释应能追溯到这些证据。

第四阶段编写的 skill 应指导以下流程（第一轮先按文档执行）：

1. 获取本次版本新增／变更 API、事件和行为契约，核对 example 的可调用能力。
2. 按业务行为形成正向／逆向场景，决定单设备或多设备；列出未覆盖项及理由。
3. 复用已有脚本与数据工具，生成符合命名及格式规范的脚本；仅按实际缺口更新工具。
4. 执行格式、引用和能力校验；核实预期依据，未知预期保留为待确认。
5. 准备环境并按脚本执行，子代理回报、主代理核验日志；按依赖处理失败，逐项复验和归因，核对断言和业务状态。
6. 归档报告，清理临时资源，将“已生成待验证”与“实际验证通过”明确区分。

新增 API 不等于机械新增一个文件；一个 API 可对应多个用例，一个场景也可覆盖多个 API。不得以当前实现的错误行为替代公开契约来生成通过条件。

### 8.1 失败处理铁律（单设备与多设备一致）

> 不得为了让 SDK 测试通过而修改测试预期、放宽断言、删除检查或跳过失败用例。只有证据证明用例违反已确认契约、前置条件或操作流程时，才能修正用例，并保留修改依据和原始失败证据。第四阶段必须将本条及以下处理规则写入 skill。

1. 失败先保存本次输入、代码与脚本版本、API 返回、事件、断言和设备状态，建立逐项失败清单。
2. 影响后续步骤／用例时暂停受影响的执行链；无依赖且状态未污染的用例继续。依赖包括账号登录、设备、群和消息等共享状态，不仅是结果引用。状态是否污染不明确时，先暂停相关设备或共享资源上的执行。
3. 主代理依据证据安排逐项受控复验，核实前置条件，关联原始执行与复验记录；不无限重试，不用随后一次成功抹去首次失败。
4. 归因区分用例问题、SDK 问题、环境问题、工具问题、尚未确定；未确定时记录证据缺口，不为了结项强行归因。
5. 有依据的用例错误可以修正并重验；SDK 缺陷保持正确用例及原定断言，生成可复现记录，修复另行决定。SDK 修复后使用同一正确用例再验。原已确认屏蔽的历史崩溃保留为显式例外，不将其推广为新失败的自动跳过规则。
6. 清理结果单独记录；恢复状态并确认前置条件后才能继续相关依赖链，不能重跑后直接把原阻塞记录改成通过。

### 8.2 工具验收与 SDK 测试结果分开

“执行完成”允许包含真实 SDK 失败；“用例通过”必须满足原定断言。工具正确运行、失败证据完整且可复现并完成必要分析时，可带着真实 SDK 缺陷交付用户人工抽验。工具故障、用例错误、关键场景未实际执行或证据不足仍是工具验收缺口；不声称阶段全部通过。待分析项单列，不伪装成已确认 SDK 缺陷。

## 9. 人工使用要求

- 未启用 AI 模式时，example 保持人工操作入口；不自动执行测试、等待主代理或强制登录某个脚本账号。
- 人工可完成初始化、登录／退出、搜索 API、编辑 JSON 参数、调用和查看返回值及错误信息。
- 本次验收范围是保持现有人工能力，并补齐本次脚本涉及的 API，不承诺 SDK 全量公开 API 的人工覆盖。本次纳入脚本的 SDK API 同样应可从人工入口找到并调用；脚本专用的协调和文件辅助操作不必暴露为 SDK API。
- 人工能够查看相关异步事件、识别调用结果，取得必要资源 ID 后继续下一次调用，完成有依赖的 API 抽验。
- 人工和 AI 使用相同 SDK 调用及结果转换，避免两种模式实际验证不同实现。
- 配置和 Token 准备方式有清晰说明；结束 AI 运行或删除其临时目录后，人工模式仍能启动和使用。

## 10. 分阶段交付与验收

### 第一阶段：实现测试体系，AI 实际执行、复验和分析

交付集中入口、数据／日志／执行支持工具、脚本规范与校验、单设备正向／逆向脚本和多设备交互脚本，保留人工功能。以现有 5.0.0 脚本所覆盖能力为迁移基线，补充业务断言，不无故丢失覆盖；已有已知问题和未覆盖项显式保留。

验收要求：

- Android、iOS 分别验证适用的单设备正向与逆向脚本，报告可追溯；平台差异单独记录。
- 完成第 7.1 节三个典型场景的主／子代理实际执行；记录实际设备组合，不将该结果扩展为未测组合已通过。环境不满足的场景保持阻塞并说明原因，不宣称第一阶段全部通过。
- 验证监听就绪后才触发、事件匹配、阶段输出传递、超时／失败阻塞；证据不满足时不能误报通过。
- 验证非法脚本在 SDK 操作前被拒绝，缺失配置或环境能力报告明确原因。
- 按本规格、计划和脚本完成从平版产物到用例编写、校验、执行、日志核验、失败复验及证据归档的一次完整流程；不提前编写 skill。
- 验证失败仅阻塞受影响链，无关用例继续；逐项分析失败，不为迎合 SDK 结果修改用例。工具验收与 SDK 结果按第 8.2 节分别报告，真实 SDK 缺陷不要求在本任务中修复。
- 确认临时产物和报告被 Git 忽略，删除已结束运行的临时目录不破坏报告和人工配置。
- 完成 example 相关必要检查和人工入口基本可用性检查；不能代替第二阶段用户抽验。

### 第二阶段：用户亲自进行人工抽验

第一阶段完成后提供启动方式、准备数据、API 清单、参数示例和预期结果，由用户亲自选择并抽验。建议覆盖正常／错误参数调用、有依赖的数据操作及异步事件查看。

本阶段以用户实际反馈为依据。AI 脚本通过或 AI 操作界面均不能替代用户验收；用户尚未试用时标记“待人工抽验”。测试体系问题修复后，重验受影响的 AI 用例，并交由用户复验人工路径；SDK 缺陷另行决定修复，不能通过修改正确用例消除失败。

### 第三阶段：旧 AI 内容清理（待讨论，未确定）

在前两阶段之后另行讨论现有重复 AI 内容的清理范围。届时盘点旧脚本、工具、文档以及 CI 的引用和共享依赖，再确定保留、迁移和删除清单及验证方式。

当前不确定删除清单，不删除 CI 工作流或共享工具，不将整个第三阶段算入第一阶段验收。第一阶段可为新入口做必要适配；涉及 CI 依赖的旧内容暂保留，不因接受格式不兼容就提前清理。

### 第四阶段：根据已跑通的流程编写 skill

在前三阶段实际执行与验证结果基础上，再编写名称待定的新测试 skill。固化与 `platform-sdk-porting-v2` 的交接、工具调用、脚本制作、主／子代理协同、证据核验、依赖暂停与继续、逐项复验及失败处理铁律，不在第一阶段提前编写。第三阶段的具体范围仍另行讨论。

skill 编写后用一个代表性场景复跑，检查实际操作能否按 skill 复现；不能只检查文档格式。第一轮流程执行不依赖该 skill，因此不存在先写 skill 才能完成前三阶段的循环依赖。

## 11. 评审与后续设计边界

框架、四阶段顺序、用例范围、协同方式和失败处理规则已确认。配套样例用于固定认知，不代表运行器已经支持；第一阶段仍需落实格式校验、控制通道和日志工具接口，第四阶段再确定 skill 名称和发现方式。保持最小实现，优先局部改造。

第三阶段的范围是明确延期的决策，不妨碍前两阶段推进。规格评审通过不表示四个阶段已经完成，也不自动授权 Git 提交或推送。
