# testing_v2 测试执行规格

目标：通过 Dart CLI 完成可重复执行、可追溯的多设备协同系统测试。单设备执行暂缓。

框架入口：[测试执行流程](../../testing_v2/docs/2026-11-06-test-execution-flow.md)。协作约束遵循 [testing_v2/spec.md](../../testing_v2/spec.md)。本文路径除特别注明外，均相对 `testing_v2/`。

## 1. 系统边界与编排

1. 工程使用 Dart 实现；宿主命令由 Dart 调用，不使用 Bash 串联测试流程。
2. 各模块职责单一，可独立调用；Dart `main` 提供 CLI，支持分环节操作和全流程自动化，两种方式复用同一套实现。
3. 编写用例属于执行前准备。已经验证的用例可重复执行，不要求每轮重新编写。
4. 支持 Android、iOS 模拟器；真机与沙箱不在当前范围。
5. 保持 example 的人工使用能力及现有工具的使用方式；本次不改造单设备执行。
6. 工程独立管理代码、数据和产物，不调用其他测试体系的内部脚本，不依赖其配置或运行产物。

### 1.1 环节契约

数据生成在 CLI 启动前完成。各模块按下表交接，调度顺序见 §1.2；产物通过同一进程中的 Dart 对象传递，快照用于独立调用及排查。各环节的准入条件和完成判据见对应章节。

| 环节 | 必需输入及来源 | 成功交付的产物 | 消费方 |
|---|---|---|---|
| 数据生成 | 辅助脚本的环境、账号及资源输入 | 校验后的 `lib/accounts.g.dart` | CLI 加载并固定本轮数据（§2） |
| 用例前置准备 | 已确认的准备声明、本轮角色账号、管理配置来源 | 准备操作结果及独立核验记录（§2.5） | 编排层逐用例启动与执行；执行前仍重新核验 |
| 设备准备 | 本轮指定的模拟器 | 平台、模拟器实例、运行设备 ID、就绪检查结果；保存为 `devices.json` | 构建目标选择、安装与启动（§3.2） |
| 编译 | example 工程、设备平台、构建参数 | 平台、构建参数、应用标识、产物绝对路径、构建日志 | 安装运行（§3.4） |
| 安装运行 | 设备准备结果、匹配的构建产物 | 设备 ID、应用标识、HTTP 端点、凭据、握手信息及检查时间 | 用例执行（§4.2） |
| 用例执行 | 用例及本轮角色对应的账号、设备、连接数据 | 运行器结束结果、每次执行报告或未完成原因、证据位置 | 汇报与排查（§4） |
| 汇报 | 本轮各阶段结果、用例执行及复验记录 | `summary.md`、`statistics.csv`、过程记录及证据引用 | 人工和 AI 判读、清理保护（§6） |
| 清理 | 选定类型、目标轮次、受保护产物 | 实际删除项、保留项及原因、失败项 | CLI 展示及操作日志（§7） |

Dart 编排层负责输入交接、汇集各接收方的验收结果及组织收尾，不实现专业校验或用例内部控制流。设备和构建可在本轮内复用；业务前置准备按用例逐次执行，不能提前批量准备互相冲突的业务状态。清理也可在下次执行前独立调用。

### 1.2 CLI 与帮助

在 `testing_v2/` 执行 `dart run bin/cli.dart <操作>`。CLI 文件参数相对调用时的工作目录解析，随后转为绝对路径；YAML 内的 `script` 路径相对 YAML 所在目录。工具根据自身位置定位仓库和产物目录，不随宿主命令的工作目录改变。操作职责如下：

| 操作 | 职责 |
|---|---|
| `prepare` | 为指定用例执行已声明的业务前置准备并核验，支持同时建立本轮测试输入；不重新生成账号源码 |
| `devices` | 查找、查看、启动、关闭、销毁设备及安装、卸载应用等基础操作 |
| `build` | 编译被测 example，返回构建产物位置 |
| `launch` | 使用设备 ID 和构建产物安装、启动 App，检查控制服务 |
| `run` | 使用已就绪的执行端运行多设备用例 |
| `report` | 根据本轮执行记录生成汇总报告 |
| `clean` | 按类型及轮次清理允许删除的产物 |
| `all` | 对显式指定的用例依次组织设备准备、编译、安装运行、执行、报告及选定清理 |

顶层及各操作提供 `--help`，说明用途、参数、前置条件、输入输出位置、调用示例和退出结果含义。帮助查看不执行设备或测试操作；数据生成辅助脚本独立于上述 CLI 流程。

所选操作成功完成且没有未处理的执行、报告或收尾故障时返回 0，否则返回非零；用例执行还要求本次用例通过。用例结论与任务故障分别保存，不能只凭 CLI 退出码判断 SDK 行为。

`all` 接收显式用例选择文件，不扫描目录默认执行全部用例。设备准备、编译完成后，按列表逐例执行“前置准备及核验 → launch → run”；用例间串行，用例内部并发由 YAML 控制。独立调用使用相同模块，`run` 不隐式准备业务状态、安装或重启 App。未指定清理类型时保留产物。

后续用例重新核验自身账号、设备和业务前置条件；前一用例失败不直接判定后续用例失败。外部操作结果未知或业务状态可能污染后续用例时，阻断共享该资源的用例，直到查证；不据“App 已重启”推断影响已消除。混合 Android/iOS 的协同场景须在用例确认时明确，不作为默认选择或本轮额外验收要求。

**建轮与参数契约**：

| 调用形式 | 必须满足的行为 |
|---|---|
| `all --cases <文件>` | 新建测试轮次、固定输入并执行列表；不能用此入口恢复已有轮次 |
| `prepare <用例.yaml> --cases <文件>` | 分环节建轮入口；固定列表及账号快照，只准备指定用例，该用例须在列表中 |
| `prepare <用例.yaml> --run-id <ID>` | 在已有测试轮次准备指定用例，不刷新账号或角色映射 |
| `devices <子操作> [--run-id <ID>]`、`build [--run-id <ID>]` | 有 ID 时并入指定轮次；无 ID 时创建独立操作轮次，仍保存日志、设备清单或构建产物，不要求账号数据 |
| `launch <用例.yaml> --run-id <ID>` | 使用该用例全部角色及登记的匹配构建；返回一个完整启动操作标识 |
| `run <用例.yaml> --run-id <ID> --launch <启动标识>` | 使用且核验这一组连接；不接受多个启动标识，不自动选取或拼接 |
| `report --run-id <ID>` | 汇报明确指定的轮次 |
| `clean --run-id <ID> --type <类型>` | 显式选择缓存、日志、构建、报告或全部；`--type` 可重复，值为 `cache/logs/build/reports/all` |

`--cases` 与 `--run-id` 互斥。`--cases` 建轮时由工具生成并输出新 ID，源文件不另存 `runId`；已有 ID 必须存在且可读取，不因拼写错误静默创建。独立操作轮次不补录为测试轮次，已有设备和构建可通过显式设备 ID、构建路径作为新测试轮次的输入。`all` 支持相同的 `--type` 清理选择，作用于它新建的轮次。

`prepare/run/all` 涉及管理通道时使用 `--data-input <JSON路径>` 指定 §2.3 的输入来源；未涉及时不要求。`run/all` 可用 `--flow-timeout-ms <正整数>` 覆盖 YAML 值。设备子操作参数及构建产物选择参数由实现计划统一定义，必须满足指定目标、拒绝歧义的规则。

用例选择文件不纳入 Git，可放在 `tmp/`；只保存用例列表和角色选择，不保存 Token 或管理配置。例如该文件位于 `tmp/cases.json`：

```json
{
  "cases": [
    {
      "yaml": "../data/5.0.0-multi-presence-positive.yaml",
      "roles": {
        "alice": {"accountId": "user_a", "platform": "ios", "instance": "<UDID-A>"},
        "bob": {"accountId": "user_b", "platform": "ios", "instance": "<UDID-B>"}
      }
    }
  ]
}
```

`cases` 有序、非空，每项 `yaml` 相对选择文件所在目录解析；`roles` 遵循 §2.4。建轮时规范化路径，调用执行模块的静态解析入口交付 §1.4 的 `CaseDefinition`，固定列表、角色及用例副本到本轮；后续不重读选择文件。分环节的用例参数用于匹配已登记的源路径，不隐式追加或替换定义。轮次输入固定前失败只记录初始化故障，不开始设备或业务操作。

### 1.3 交接与失败规则

1. 每次模块调用返回成功或失败、实际产物及证据位置；失败必须带错误。调用结束与调用成功分别判断，部分成功不得提升为整个阶段成功。
2. 编排层统一维护 `runId`、本次输入、阶段结果及产物引用，在调用前后保存快照到 `tmp/<runId>/run.json`。快照同时提供清理所需的任务状态、故障状态及证据引用（§5.1、§7）。只有通过该阶段完成检查的产物，才能满足后续准入条件。
3. 准备失败只阻断依赖其结果的用例；其余用例按自身前置条件判断。汇报必须接收失败、未执行及中断记录，不能因前置阶段失败而直接跳过。
4. 消费已有输入的分环节调用必须指定轮次并核验产物及外部状态；新建轮次及独立设备、构建调用遵循 §1.2。不得自动选“最近一次”目录，也不得拿当前账号文件替换该轮输入。输入缺失、损坏或状态失效时，列明缺项及需重做的环节。
5. 快照记录已发生的操作，不授权重放业务命令。仅有调用开始记录时，结果为未知；恢复前先查证外部结果，不能默认成功或自动重发。
6. 设备启动、安装、HTTP 检查及用例执行须有有限等待上限，并记录所用值；到期记录超时及仍可能运行的操作。超时不证明进程、SDK 调用或服务端副作用已停止。
7. 同一轮只允许一个修改状态或产物的 CLI 操作；运行、报告生成和清理不能并发写同一轮。同一设备不能同时分配给两个正在执行的任务，冲突须明确拒绝。

### 1.4 交付格式与接收验收

本节约束模块开发和联调。上游负责按契约交付，下游负责在使用前验收，编排层只传递结果、记录验收并阻断依赖操作。各入口复用同一契约；专业校验由所属模块提供，接收方调用，不复制另一套规则或自行代做上游操作。

**公共格式**：模块返回 `OperationResult<T>`，下表字段均须存在。生成脚本的模块调用也遵循此格式，但不要求 CLI 读取脚本上次运行记录；CLI 验收实际加载的数据。此格式不改变生成源码的导出形式和 `flow_runner` 原始报告。

| 字段 | Dart 类型及约束 |
|---|---|
| `runId` | `String?`；CLI 内必填且与调用轮次一致，CLI 前的数据生成使用 `null` |
| `operationId` | 非空 `String`；标识本次调用，轮内唯一，生成操作独立分配 |
| `status` | 枚举 `success/failure`；表示模块操作结果，不等于用例通过 |
| `data` | `T?`；成功时必填，失败时可保留符合 `T` 格式的已有结果，否则为 `null`；失败结果可供排查汇报，不能作为成功产物准入 |
| `errors` | `List<OperationError>`；成功时为空，失败时非空 |
| `evidence` | `List<EvidenceRef>`；关联本次调用证据，缺失证据须在错误中说明 |

`OperationError` 为 `{message: String, field: String?, expected: JsonValue?, actual: JsonValue?}`；消息非空，拒收时后三项必须指出不合格字段及预期、实际，缺失实际值使用 `null`。`EvidenceRef` 为 `{path: String, location: String?}`，以绝对路径指向实际文件；`location` 为行号、操作标识或事件序号，`null` 表示整个文件，不得只引用目录。错误和证据写出时脱敏。

下表使用 `JsonObject = Map<String, Object?>`；`JsonValue` 仅为 JSON 的字符串、数字、布尔值、`null`、列表或对象。列出的交付字段必须存在，`?` 字段允许 `null`；`String` 标识及路径均非空，不能静默转换错误类型。Dart 的 `DateTime` 写为带时区的 ISO 8601 字符串，枚举写其名称；其余字段名称及类型与 JSON 一一对应。业务配置仍按 SDK 类型校验，不能只检查“是一个 Map”。

`FileRef` 为 `{path: String, sha256: String}`，路径使用绝对路径，摘要为小写十六进制 SHA-256。文件摘要计算原始字节；目录递归枚举但不跟随符号链接，按使用 `/` 分隔的相对路径排序为 `[路径, 类型, 内容]` 清单：类型为 `file/directory/link`，内容分别为文件摘要、`null`、链接目标字符串；对无缩进 JSON 清单的 UTF-8 字节计算摘要。构建目录中的链接不得指向副本以外。运行中追加的日志使用 `EvidenceRef`，不要求提前计算终态摘要。

**各模块的 `data` 类型**（花括号表示字段定义，不是额外的脚本语法）：

| 交付类型与生产方 | 字段及内容 |
|---|---|
| `AccountData`，账号生成／加载 | `environment: JsonObject`，内容遵循 §2.1；生成脚本另外以证据引用交付的源码位置，加载模块返回实际读到的数据 |
| `CaseDefinition`，执行模块的静态解析入口 | `name: String`、`sourceYaml: String`、`sourceJson: String`、`yaml: FileRef`、`json: FileRef`、`requiredBindings: List<String>`；源路径用于追溯，文件引用指向本轮固定副本；解析后的 `FlowSpec` 仅在内存传递 |
| `CaseData`，数据模块 | `caseName: String`、`attempt: int`、`accounts: Map<String, JsonObject>`、`initConfig: JsonObject`、`input: JsonObject`；正整数执行序号，账号按角色映射为 `{userId: String, userToken: String}`，业务输入及唯一值遵循 §2.4 |
| `PreconditionResult`，数据模块 | `caseName: String`、`appKey: String`、`checks: List<PreconditionCheck>`、`setup: FileRef?`、`check: FileRef`；无声明时 `checks` 为空，纯核验时 `setup` 为 `null` |
| `DeviceResult`，设备模块 | `platform: android/ios`、`instance: String`、`deviceId: String?`、`observedState: String`、`checkedAt: DateTime`、`ready: bool`；就绪结果必须有运行设备 ID；查找／查看返回 `List<DeviceResult>`，未就绪设备也可正常列出 |
| `BuildResult`，构建模块 | `platform: android/ios`、`architectures: List<String>`、`applicationId: String`、`mode: debug`、`arguments: List<String>`、`artifact: FileRef`；架构非空，产物为本轮副本，参数遵循 §3.3 |
| `LaunchResult`，启动模块 | `caseName: String`、`roles: Map<String, Connection>`；外层 `operationId` 即启动标识，成功时角色集合完整；`Connection` 字段见 §3.4 |
| `ExecutionResult`，执行模块 | `caseName: String`、`attempt: int`、`definition: CaseDefinition`、`launchOperationId: String?`、`verdict: String`、`report: FileRef?`、`required: List<RequiredCheck>`、`finish: Map<String, FinishResult>`；结论只取 `是/否/未执行/未完成`；未启动解释器时报告为空，未使用连接时启动标识可为空，不能伪造报告或收尾结果 |
| `ReportingResult`，汇报模块 | `summary: FileRef`、`statistics: FileRef`、`process: List<FileRef>`、`attempts: List<AttemptRef>`、`dependencies: List<ReportDependency>`；总结、统计及过程文件与证据依赖遵循 §6 |
| `CleanupResult`，清理模块 | `deleted: List<String>`、`kept: List<PathReason>`、`failed: List<PathReason>`；三组路径不重叠，部分删除失败时仍交付完整清单，外层状态为 `failure` |

嵌套类型：

- `PreconditionCheck = {users: List<String>, expected: none/friends, actual: Map<String, bool>?, satisfied: bool, checkedAt: DateTime}`。`users` 恰好两个不同账号；`actual` 按账号记录其列表是否含对方，查询失败为 `null` 且 `satisfied` 为 false，错误由外层交付。
- `RequiredCheck = {binding: String, recordIndices: List<int>, passed: bool, evidence: List<EvidenceRef>}`，索引对应报告 `steps` 的零基位置，判据见 §4.1。
- `FinishResult = {success: bool, error: String?}`，失败必须带错误；`AttemptRef = {caseName: String, attempt: int}`，序号为正整数。
- `ReportDependency = {report: String, evidence: EvidenceRef}`；`PathReason = {path: String, reason: String}`，原因非空。

**接收检查及退回对象**：每次调用检查当前必需输入；类型正确不能代替归属、内容和外部状态检查。不得等到派发业务命令后才发现本可提前检查的缺项。

| 交接 | 接收方开始前必须验收 | 不合格时需处理的环节 |
|---|---|---|
| 生成 → 加载、建轮 | 数据加载模块复用 §2.1–2.3 的完整字段校验；建轮核对账号选择和角色集合 | 数据内容交回数据准备；角色选择交回调用输入 |
| 用例 → 准备、执行、汇报 | 执行模块静态解析并校验命令 ID、必要绑定及配套文件，业务数据和准备声明调用数据模块校验；其他模块只消费同一 `CaseDefinition` 和固定数据 | 用例定义；传错副本则是编排问题 |
| 数据准备 → 执行 | 执行入口核对 `caseName/attempt`、角色账号、只读数据布局；调用数据模块重新核验声明状态，确认实际账号、应用及观测属于本次调用 | 数据准备或调用映射；`run` 不自行恢复业务状态 |
| 设备 → 构建、安装启动 | 构建只核对所需平台；安装启动调用设备模块复核目标身份及 §3.2 就绪判据 | 设备准备；不以构建成功证明设备可用 |
| 构建 → 安装 | 安装方检查产物摘要、应用标识、平台、架构和控制模式构建参数；不能只检查路径存在 | 构建副本或构建操作 |
| 启动 → 执行 | 执行入口核对完整启动组、设备、构建引用、未占用／未失效状态，并按 §3.4 重新握手 | 启动；若设备已失效，先处理设备 |
| 执行 → 汇报 | 汇报核对用例及执行序号、固定定义、报告摘要和证据引用，使用 §4.2 的统一判据；失败、未执行及未完成记录均须接收 | 执行产物缺陷交回执行模块；已丢失证据保留缺口，不冒充原次结果补跑 |
| 汇报 → 编排、清理 | 编排验收文件及 §6 对账结果；清理读取已登记依赖并按 §7 检查保护范围，引用不明不删除 | 汇报文件或依赖登记；编排错传归属时修编排 |
| 清理 → 编排 | 逐项核对所选范围与删除、保留、失败清单；只有确认不存在的路径可更新为已删除 | 清理操作或登记更新；不能用删除失败解除保护 |

拒收时记录生产方、接收方、来源 `operationId`、不合格字段、预期、实际、证据及需重做的环节；该记录归入本次操作结果和故障记录。接收方立即停止依赖该输入的操作，不以默认值掩盖必填缺项、换用旧产物或隐式调用上游返工。记录故障、必要收尾和汇报仍须执行；完整记录一次测试失败，是有效交付，不能要求上游把 SDK 失败改成通过。

返工后重新验收受影响的交付。账号配置或用例定义更换时新建轮次；设备关闭、销毁、应用卸载、重新安装或启动使受影响的旧连接失效。新构建不改写已有安装记录，使用它须显式安装启动；不因此废弃无关设备和产物。返工保留历史，不自动重放结果未知的业务操作。

开发时，上游测试验证实际输出符合契约，下游测试验证合格输入可用、缺项／类型错误／归属错误／状态失效被拒收，并确认拒收前没有依赖该输入的副作用。联调须将上游实际返回值交给下游验收，不能只各自使用手写样本。输出违约修上游，验收误判修接收方，错传输入修编排；交付后外部状态变化记录为状态失效，不据此推断上游有 bug。契约本身需调整时先确认，不以修复为由转移职责或放宽条件。

## 2. 数据准备

详细约定：[数据准备](../../testing_v2/docs/2026-11-06-data-preparation.md)。

### 2.1 生成产物

`lib/accounts.g.dart` 导出 `const Map<String, Object?> environment`，文件不纳入 Git。缺少文件表示数据准备未完成。

| 数据 | 规则 |
|---|---|
| `appKey` | 必填，与账号 Token 所属应用一致 |
| 初始化参数 | 使用 SDK 字段名；如 `debugMode`、`dataSyncType`、`enableUserInfo`，按实际配置生成 |
| `accounts` | 非空对象列表，每项 `id/token` 为非空字符串，`id` 唯一；数量由用例需求决定，不在此绑定设备 |
| `groups` | 对象列表，每项 `id` 为非空字符串，可选 `owner/name` 为字符串；不需要时为空列表 |
| `rooms` | 对象列表，每项 `id` 为非空字符串，可选 `name` 为字符串；不需要时为空列表 |
| 私有部署参数 | 按需生成 `enableDNSConfig: false`、`restServer`、`imServer`、`webSocketServer` 及指定的端口 |

生成产物不得包含管理端凭据（`clientId`、`clientSecret`、应用 Token）、设备信息、API 返回值或监听事件。初始化数据准备成功不代表 SDK 已初始化或账号已登录。

### 2.2 生成行为

1. 辅助脚本位于 `scripts/`，纳入 Git；在 CLI 启动前读取输入、获取账号 Token、校验数据并生成 Dart 源码。`appKey`、账号 `id/token` 必须为非空字符串，账号 ID 不得重复；资源列表及初始化参数须符合对应 SDK 类型。
2. 全部数据获取、校验及源码生成成功后，整体替换目标文件并返回成功；任一账号获取失败则本次生成失败，保留原文件且返回非零结果。文件存在不能代替本次生成结果，也不能证明 Token 当前仍有效。
3. 不覆盖 example 的配置及生成文件，不擅自重置服务端业务状态。生成数据不执行 SDK 初始化、登录或设备操作。
4. CLI 将实际加载的 `environment` 固定为本轮输入，保存在 `run.json` 的 `environment` 字段；角色绑定从该副本选取账号。不得在一轮中重新读取已改写的源码混用数据；更换初始化配置或账号数据须重新启动 CLI、创建新轮次。含凭据的快照按 §5.3 受限保存，不作为可直接分享的报告。

### 2.3 生成输入与加载

生成脚本显式接收本地 JSON 路径，不搜索其他工程配置。输入不纳入 Git，可放在 `tmp/`；该人工提供的源文件不登记为可自动清理的运行缓存。

| 输入 | 约束及用途 |
|---|---|
| `appKey`、初始化及私有部署参数 | 与 §2.1 使用相同顶层字段；初始化配置不得从设备或历史报告反推 |
| `accounts` | 非空列表，每项为含非空 `id` 的对象；生成脚本获取各账号 Token，不创建账号 |
| `restApi`、`clientId`、`clientSecret` | 同一 JSON 顶层的非空字符串；REST 服务地址及管理凭据，仅由数据模块消费，不写入生成源码或运行快照 |
| `groups`、`rooms` | 读取已有资源标识，结构遵循 §2.1，省略时为空列表；不自动创建、删除资源 |

将 `appKey` 解析为 `org#app`，向 `restApi/org/app/token` 发送 `client_credentials` 请求获取应用 Token，再携带该 Token 以 `inherit` 请求为指定账号获取用户 Token，不启用自动创建用户。HTTP 失败、响应结构错误或缺少 Token 均判生成失败。`restApi` 是数据准备通道，不等同于 SDK 的 `restServer`。管理凭据不通过命令行明文值传递；日志只记录来源文件及脱敏错误。

CLI 主入口及无账号依赖的模块不得静态导入 `accounts.g.dart`。仅建立需要账号的新轮次时，数据模块按需启动独立 Dart 数据加载入口，由该入口导入生成文件并通过受控输出返回 `environment`；捕获输出后复用生成端的 §2.1 字段、SDK 类型及禁止内容校验，再交付 `AccountData`，不转印原始输出。加载成功不代替数据验收；错误只报告类型和位置，不输出可能含 Token 的源码片段。生成文件缺失或不可加载时，拒绝依赖账号的操作；帮助、设备操作、构建、已有轮次的报告与清理仍可使用。加载入口的代码组织在实现计划中确定。

已有轮次读取快照中的 `environment`，不重新加载生成源码；快照无本轮数据时拒绝执行，不能以当前生成文件补齐。加载完成不代表 Token 当前有效，实际登录结果由用例判定。

Token 有效性与测试结论分开处理：执行前若已有权威的过期或失效证据，阻断依赖该 Token 成功登录的用例并提示重新生成数据；没有可靠证据时不猜测有效期，也不增加未经验证的探测接口。执行中登录失败保留实际结果及断言结论，再按证据归因，不自动改成“未完成”或认定 SDK 缺陷。故意使用无效 Token 的逆向用例按预期 SDK 错误判定；控制服务 HTTP 401 是配对凭据问题，不能当作 SDK Token 错误。更新正常登录所需账号 Token 后须建立新轮次。

### 2.4 用例数据与角色绑定

每个用例由同目录、同主文件名的 YAML 和 JSON 组成；JSON 为该用例的唯一元数据入口，所有角色的 `script` 指向它。`steps` 保存完整命令与参数，`requiredBindings` 遵循 §4.1；顶层 `data` 保存业务输入及 §2.5 的可选前置准备声明。例如：

```json
{
  "data": {
    "input": {"expiry": 120},
    "unique": {"presenceDescription": "presence-"}
  },
  "requiredBindings": ["global.biz.event.presence_received"]
}
```

上例省略 `steps`。`data.input` 为 JSON 对象；`data.unique` 为字段名到字符串前缀的映射。两者省略时为空对象，字段名不得重叠。数据模块接收编排层分配的轮次、用例和执行序号，拼接前缀、`runId`、用例文件主名、执行序号及字段名，生成唯一值并合并为本次 `biz.input`；复验重新生成，不能重复使用首次标识。不在 JSON 中放延时、分支或调度规则。

建轮时保存 YAML、JSON 原文副本及摘要到 `tmp/<runId>/cases/<用例文件主名>/`。准备、执行、复验和汇报均使用这份定义；源文件后来修改不改变本轮，用新定义须新建轮次。副本缺失或摘要不符时拒收，不以当前源文件补齐。执行模块解析时仅将配套 JSON 的引用定位到本轮副本，保持流程和命令语义，源路径仍用于追溯；不能让 YAML 副本中的绝对 `script` 路径绕过固定副本。

CLI 接收每个用例的显式角色映射，形状为 `{角色: {accountId, platform, instance}}`。角色集合必须与 YAML `agents` 完全相同；`accountId` 精确匹配本轮账号 ID，`platform` 为 `android` 或 `ios`，`instance` 为 AVD 名或 iOS UDID。编排层保存映射，设备模块补充运行设备 ID；不按列表顺序推断绑定，不把账号选择交给设备模块。同一用例不同角色对应不同设备；是否共用账号由场景决定。

角色名、`data.unique` 字段名及点路径中的对象键须符合解释器标识符规则 `[A-Za-z_][A-Za-z0-9_]*`；`as` 与 `requiredBindings` 使用相同路径规则，列表索引仍用数字。非法名称在派发前报错。账号 ID、设备 ID 是字段值，不受此命名限制。

用例业务数据统一使用 `$global`；不同时注入 `$config`、`$agents` 等同义业务数据。流程局部变量仍遵循解释器作用域。数据模块交付 `CaseData`；编排层只组织角色和设备对应关系，执行模块验收后以本次数据创建 `GlobalData(initial, outputRoots: ...)`，不在编排层实现 SDK 字段筛选。布局及写入责任如下：

| 引用区域 | 提供者与设置时机 | 内容及使用者 |
|---|---|---|
| `$global.device.<role>` | 启动检查通过后，由编排层固定 | `platform`、`instance`、`deviceId`、握手 `instanceId`；用于场景条件与定位，不包含控制 Token |
| `$global.account.<role>` | 数据模块按已固定映射从本轮数据选取 | `{userId, userToken}`，分别取账号 `id/token`；供登录命令及身份断言使用 |
| `$global.biz.config.initConfig` | 数据模块由本轮 `environment` 构造 | 包含 `appKey`、SDK 初始化参数及私有部署参数，排除 `accounts/groups/rooms` 及 Token；供 `ChatClient.init` 使用 |
| `$global.biz.input` | 数据模块在每次尝试前生成 | 用例常量、本次唯一值；`groups/rooms` 从本轮数据提供，这两个名称保留，不允许用例覆盖 |
| `$global.biz.result.<binding>` | 解释器在命令返回后写入 | 完整结果对象；后续步骤通过 `.data` 等明确字段读取 |
| `$global.biz.event.<binding>` | 解释器匹配事件后写入 | 匹配事件的 payload；原始序号、来源另存证据 |

`initial` 的根为 `device/account/biz`，不额外包一层 `global`；`biz.result`、`biz.event` 初始为空对象。`outputRoots` 固定为 `global.biz.result` 和 `global.biz.event`，其他区域只读。输出路径单次绑定，不读取隐含“最新结果”；路径缺失、结果未产生和合法 `null` 遵循解释器规则。执行及复验各自创建数据视图，不从上次输出恢复业务执行。

### 2.5 业务前置条件

数据模块负责业务前置准备及核验，编排层按用例调用。YAML `preconditions` 声明必须满足的状态；只有 JSON `data.prepare` 明确列出的状态才允许由工具准备。场景及允许改动的角色、资源在用例设计时确认，不要求每轮提供人工审批文件。初始化、登录、订阅等 SDK 流程动作仍由用例命令执行。

`data.prepare` 是可选数组，省略或为空时只核验。每项沿用 `preconditions` 的数据形状，必须与一项 YAML 前置声明一致，不增加控制流语法。例如邀请加好友用例的前置为非好友：

```json
{"data": {"prepare": [{"contacts": {"between": ["alice", "bob"], "state": "none"}}]}}
```

当前只支持联系人关系，角色必须绑定两个不同账号。同一声明列表内，针对同一账号对的重复或冲突项拒绝执行。数据模块通过管理 REST 查询双方列表：`none` 要求双方均不包含对方，`friends` 要求双方均包含对方；准备只处理该账号对，不删除其他联系人、不创建账号。已经满足时不写入；否则按声明增删，完成后重新查询双方状态，不能用 HTTP 请求成功代替准备成功。测试邀请流程时不能把前置准备成“已是好友”，以免提前完成被测行为。

| 管理操作 | 通道及约束 |
|---|---|
| 核验 | `GET /<org>/<app>/users/<id>/contacts/users`，分别查询双方；成功响应须为可识别的联系人列表 |
| 准备 friends | 对指定账号对使用 `POST /<org>/<app>/users/<a>/contacts/users/<b>`，再核验双方 |
| 准备 none | 对指定账号对的两方向按实际状态使用 `DELETE /<org>/<app>/users/<a>/contacts/users/<b>`，再核验双方 |

地址以 `restApi` 为基址，路径中的用户 ID 做 URL 编码。`--data-input` 提供 §2.3 的配置来源，数据模块确认应用与本轮 `appKey` 一致，通过管理凭据获取应用 Token；只核验时不使用写接口，需准备时必须具备对应写权限，不替换本轮账号数据。分别记录鉴权失败、权限不足、网络或超时、响应无效、状态不满足；请求错误不当作空联系人列表。写请求结果未知时停止该项准备并交付查证信息，不盲目重发。

`prepare` 独立可调用，`all` 在每个用例前调用同一模块；`run` 只重新核验，不隐式修复业务状态。独立复验需要恢复前置状态时先显式 `prepare`，再 `launch/run`。准备失败阻断受影响用例，不扩大修改范围，也不继续执行该用例。

准备操作写入 `tmp/<runId>/preconditions-setup-<操作标识>.json`，保存用例、声明、实际账号、准备前观测、执行动作及结果；核验另写 `preconditions-check-<操作标识>.json`，保存时间、预期与实际、是否满足及证据。两者由快照关联，不覆盖此前记录。每次 `run` 仍将最新核验写入本次执行目录的 `preconditions.json`，无声明时为空列表；不能沿用准备时或上次执行的满足结论。

## 3. 设备准备、编译与安装运行

详细约定：[设备准备](../../testing_v2/docs/2026-11-06-device-preparation.md)。

### 3.1 基础操作

通过 `dart:io` 的 `Process.run`、`Process.start` 调用 `adb`、`emulator`、`xcrun simctl` 等宿主命令，取得输出、退出码及进程状态。

| 操作 | 必须满足的行为 |
|---|---|
| 查找 | 查找宿主环境中的模拟器 |
| 查看 | 提供可用模拟器及运行状态 |
| 启动 | 启动指定模拟器 |
| 关闭 | 关闭指定模拟器，保留实例及数据 |
| 销毁 | 删除指定模拟器实例及其数据 |
| 安装 | 将已有的 example 构建产物安装到指定模拟器 |
| 卸载 | 从指定模拟器卸载 example |

### 3.2 产物与交接

基础操作按 §1.4 返回 `DeviceResult` 及操作结果。编排层将结果汇入 `tmp/<runId>/devices.json`，形成带观测时间的设备清单；操作过程按 §5.2 留存。`ready` 只有通过就绪检查才为 true，`observedState` 保留平台的实际状态或明确的 `unknown`，不能从操作成功推导就绪。

设备准备交付运行设备 ID，不交付仅能用于启动的模拟器名称。启动命令返回成功后，仍须完成下列检查；任一检查失败或超时，该设备不得标记就绪。

| 平台 | 设备 ID | 就绪判据 |
|---|---|---|
| Android 模拟器 | adb serial，例如 `emulator-5554` | serial 对应指定 AVD；`adb -s <serial> get-state` 为 `device`，`shell getprop sys.boot_completed` 为 `1`；`flutter devices --machine` 包含该 ID |
| iOS 模拟器 | UDID | `simctl` 中目标处于 `Booted`，`xcrun simctl bootstatus <UDID> -b` 成功；`flutter devices --machine` 包含该 ID |

不得根据设备列表顺序选择“第一个”设备；匹配不到或无法唯一匹配时明确失败。单独查找、查看操作可以返回未启动设备，但此结果不满足用例执行的设备前置条件。

| 清单内容 | 必须记录的信息 |
|---|---|
| 归属 | `runId`；已分配角色时记录角色名，单独查找设备不要求绑定角色 |
| 设备定位 | 平台、模拟器实例标识（Android AVD 名称或 iOS UDID）；运行时标识在可获得时记录（如 Android adb serial） |
| 观测状态 | 设备实际状态及观测时间；未检查、无法确认必须标明，不能当作可用 |
| 应用信息 | 安装、卸载涉及的应用标识及检查结果；安装时记录构建产物位置 |
| 操作结果 | 操作标识、操作内容、结果；失败时附错误及证据位置 |

交接规则：

1. 同一次全流程通过 Dart 结果传递数据；分环节操作从明确指定的 `runId` 读取清单。两种入口使用相同信息，不从文本日志反推结果。
2. 编译环节使用设备平台确定构建目标，安装运行环节使用设备 ID 定位目标设备。设备模块不选择登录账号，也不消费业务命令结果。
3. 设备清单只是观测快照。后续使用前须核验目标设备状态；App 连接信息由安装运行环节取得，不从设备清单猜测。
4. 报告与排查使用清单定位设备及证据；失败设备保留失败记录，不能沿用先前成功状态冒充本次成功。更新清单不覆盖历史操作日志。

### 3.3 编译契约

工作目录为仓库的 `im_flutter_sdk/example/`。控制服务仅在 Debug 且 `API_CONTROL=true` 时启用，不能使用普通人工模式产物替代。

| 目标 | 必需构建参数 | 交付产物 |
|---|---|---|
| Android 模拟器 | `flutter build apk --debug --dart-define=API_CONTROL=true` | APK |
| iOS 模拟器 | `flutter build ios --simulator --debug --dart-define=API_CONTROL=true` | 模拟器 `.app` |

1. 不同时传入 `API_SCRIPT`；其与控制模式冲突。构建使用的 Flutter 版本遵循仓库开发环境约定，依赖未就绪时记录具体错误。
2. 构建进程退出码为 0、输出为本次构建产物且可读取，才交付成功结果；构建失败时不能回退到输出目录中已有的旧包。
3. 按 §1.4 交付 `BuildResult`。安装方检查构建参数，并从实际产物核对应用标识、平台及架构兼容性，不通过固定文件名猜测；同一兼容产物可安装到多台设备。
4. Flutter 的原始输出仍在 example 的构建目录。成功后将本次 APK 或完整 `.app` 复制到 `build/<runId>/<构建操作标识>/<平台>/`，按 §1.4 比较源产物与副本摘要，一致后交付；构建到复制完成期间不能让其他构建覆盖该输出。安装前重新核对登记摘要，失败退回构建环节，不安装或回退旧包。example 的原始构建目录不归本工具清理。
5. 显式使用其他轮次的构建时，先核验构建信息并复制到本轮 `build/<runId>/` 后登记，不能让原轮次的清理删除本轮正在使用的唯一副本。
6. iOS 模拟器保留默认本地签名，不传 `--no-codesign`；本地 ad-hoc 签名不需要开发证书。构建交付、导入及安装前验收均须通过 `codesign --verify --deep --verbose=2 <App路径>`，失败退回构建环节。

### 3.4 安装与启动契约

1. 安装前复核设备就绪及构建产物；使用指定设备 ID 调用安装、启动操作，保留每次调用结果。安装成功只表示包已安装，不能据此开始用例。
2. 从目标设备本次 App 启动的 `[AGENT_CONTROL]` 记录取得随机端口及配对凭据。iOS 模拟器由宿主直连；Android 使用指定 serial 建立 `adb forward`，记录宿主端口与设备端口映射。不得复用历史日志中的连接信息；凭据供运行数据使用，启动输出写入日志前须脱敏。
3. 使用配对凭据请求 `GET /v1/info`：须返回 HTTP 200、可解析对象、`version: 2`、与目标一致的 `platform`、非空 `instanceId` 和 `state: accepting`。拒绝鉴权失败、`uncertain`、`closed` 及未知状态；本地请求直接连接，不经宿主代理。
4. 交付设备 ID、应用标识、实际 HTTP 端点、凭据和握手结果及时间。编排层将连接保存到 `run.json` 的 `connections`，以启动操作标识分组、角色名索引，字段见下表。实例身份以握手结果为准；后续握手的实例变化使原连接结果失效，须重新准备，不能静默切换后继续旧执行。
5. 每次独立用例执行及复验使用重新启动的 App 实例，并重新发现和检查连接。执行模块按 §4.2 调用 `/v1/finish` 收尾，HTTP 客户端的命令编号每次从头分配，不能把旧服务直接用于下一次执行。重启不代表清除设备数据库或恢复服务端业务状态。
6. 所需角色全部通过检查后才能进入该用例；SDK 初始化与登录由用例命令执行。编译、安装或启动失败只阻断依赖相应产物或设备的用例。

| `Connection` 字段 | Dart 类型 | 含义及验收条件 |
|---|---|---|
| `deviceId`、`applicationId` | `String` | 实际执行端及安装应用，与设备清单、角色映射和构建一致 |
| `platform` | 枚举 `android/ios` | 与目标设备及握手一致 |
| `buildOperationId`、`artifact` | `String`、`FileRef` | 本次实际安装的构建操作及副本引用，不能因新增构建而改写旧安装记录 |
| `endpoint`、`token` | `String` | 实际 HTTP 地址与配对凭据；仅供客户端使用，快照受限保存 |
| `instanceId`、`version`、`state` | `String`、`int`、`String` | 握手身份非空，成功交付时协议为 2、状态为 `accepting` |
| `checkedAt`、`startedAt` | `DateTime` | 握手观测及本次启动时间 |
| `processId` | `int?` | 可取得的 App 进程 ID；无法取得时为 `null` 并记录缺项 |
| `forward` | `{serial: String, hostPort: int, devicePort: int}?` | Android 必填且端口为 1–65535；iOS 为 `null` |
| `usedBy` | `AttemptRef?` | 初始为空，编排层在派发前绑定用例及执行序号，一经占用不能复用 |
| `invalidatedAt`、`invalidatedReason` | `DateTime?`、`String?` | 初始为空；编排层废弃连接时同时填写，与服务端 `state` 分开记录 |

一次 `launch` 为指定用例的全部角色生成同一个启动操作标识；各端均就绪才交付可执行记录，部分成功保留证据但不能用于 `run`。重新启动同一物理设备前，编排层先将该设备已有连接标记失效，保留旧记录；新启动失败也不恢复旧连接的可用性。

独立 `run` 只读取 `--launch` 指定的完整记录，验证其属于本轮及该用例，角色、设备全部匹配且连接未使用、未失效。任何缺项均拒绝执行，不拼接多次启动的角色，也不搜索“最新一次”。派发前重新握手；身份变化、设备不匹配或服务状态不可用时，记录失效原因，不自动切换连接。发生异常后，即使没有取得命令结果，也不得清除 `usedBy` 再重用连接。

**启动日志采集**：先停止指定设备上的旧实例，再建立本次日志采集，确认采集通道就绪后启动 App。Android 使用指定 serial 的 logcat；iOS 使用 `simctl spawn <UDID> log stream` 的 App 进程日志，不依靠 `simctl launch --console*` 接收 Flutter `print()`。按设备、启动区间和可取得的进程信息筛选凭据，不能只取历史文件最后一个匹配行；不要求清空整台设备日志。

凭据解析在内存中完成，写日志前脱敏。采集与握手共享明确的启动等待上限；采集失败或无法证明记录来自本次启动时，启动不成功。启动日志中的 `instanceId` 与 `/v1/info` 的值来源不同，不进行跨来源相等比较；判断是否新实例时比较同一设备前后握手身份，并结合本次启动记录。采集进程由启动模块管理，停止及失败均须回收，不留下无人管理的后台任务。

全流程可持续采集到本次执行结束；独立 `launch` 结束时关闭其日志采集，`run` 另行采集执行区间并注明两次采集的间隔。App 的 HTTP 事件缓冲不因宿主采集进程退出而清除，执行证据仍须按本次实例的事件序号采集。

约束依据：[App 模式开关](../../im_flutter_sdk/example/lib/agent/agent_mode.dart)、[HTTP 服务](../../im_flutter_sdk/example/lib/agent/control_server.dart)、[命令服务状态](../../im_flutter_sdk/example/lib/agent/command_service.dart)、[HTTP 客户端](../../tool/flow_runner/lib/http_agent_client.dart)。

## 4. 用例与执行

### 4.1 用例要求

详细约定：[编写用例](../../testing_v2/docs/2026-11-06-test-case-authoring.md)。

1. 场景、前置条件和通过标准须与用户确认；命令依据 SDK 公开接口，并核对 example 执行端是否支持。
2. 本次编写多设备协同用例，覆盖适用的正向、逆向场景；单设备用例及执行改造不在本次范围。
3. YAML 表达流程控制；JSON 保存命令和数据，命令与参数放在一起。语法、引用及断言遵循 [flow_runner 使用说明](../../tool/flow_runner/README.md)，不另建一套解释规则。
4. 缺少执行端命令支持时须单独提出并确认，不将不可执行的用例标记为可用。
5. 不得为绕过 SDK 缺陷修改正确用例或降低断言要求。

**必要验证声明**：按 §2.4 定位与 YAML 同目录、同主文件名的 JSON，读取其顶层 `requiredBindings`，`steps` 仍保存命令。声明由 `testing_v2` 消费，不增加解释器语法。

```json
{"requiredBindings": ["global.biz.event.presence_received"]}
```

1. `requiredBindings` 为非空、无重复的非空字符串数组，每项精确对应一个 `cmd` 或 `wait_event` 节点的 `as`，例如 `as: global.biz.event.presence_received`。
2. 必要节点的 `as` 在整个流程的所有分支中唯一，且节点不位于 `for/while` 循环内部。循环场景在循环后设置最终验证节点；其他节点仍可正常使用循环和并发。
3. 这些约束在执行前通过已解析的流程结构校验；声明缺失、引用不存在、绑定重复或必要节点位于循环内时，拒绝执行。
4. 执行后按报告的 `result.binding` 匹配，每项必须恰好对应一条 `status: passed` 的记录；零条、多条或非 passed 均为必要验证未通过。记录各项匹配数量、状态及证据位置，不根据变量最终值推断执行结果。
5. 用例作者依据已确认的通过标准选择必要节点，业务条件仍由节点自身的断言验证。逆向命令按断言后的 `passed` 判定，不要求其原始 `success` 为 true；所有必要项通过也不能覆盖其他步骤的失败或超时。

### 4.2 执行与结果

**准入检查**：执行模块在派发业务命令前验收编排层传入的结果，调用数据、设备和连接检查能力完成专业核验；编排层记录结果并阻断依赖操作。失败记为未执行，并按 §1.4 交付具体差异和需重做环节。

1. `CaseDefinition` 属于本轮，固定副本摘要匹配，复用执行模块的静态解析及命令 ID 校验结果；独立调用时从同一副本重新解析，不从当前源文件加载。YAML `agents` 中每个角色均有唯一设备和明确账号来源，不按列表顺序隐式绑定。不同角色使用同一账号必须符合场景，不能被工具擅自改为不同账号。
2. `CaseData` 的用例、执行序号及角色与本次调用一致，账号来自本轮输入，设备及控制服务满足 §3；执行模块按 §2.4 组装 `global`，按 §2.5 调用数据模块取得本次前置条件核验结果。解释器只校验 `preconditions` 的形状，不会替测试工具准备业务状态；无法验证或不支持时必须阻断。
3. 校验 §4.1 的必要验证声明，使用 §5.1 登记的执行序号及独立输出位置，记录固定 YAML 的 `name`、输入和证据路径。静态 YAML 不写固定运行轮次；配套 JSON 定位到本轮副本，原始源路径单独保留用于追溯。

**接入与生命周期**：直接调用 `tool/flow_runner` 的 Dart API。`testing_v2` 执行模块负责下表操作，分环节和全流程共用该模块；不以运行器 CLI 子进程作为执行入口。

| 环节 | 执行模块的责任 |
|---|---|
| 创建执行实例 | 使用已验收的 `FlowSpec`，由数据和设备交付结果创建 `GlobalData` 并传入 `Interpreter`，不向解析器注入业务数据。每次创建独立客户端、解释器、运行数据和 `ReportCollector`，设置报告 `runId`、`flowName` 及前置声明 |
| 执行 | 调用 `Interpreter.run()`；接收过程记录及异常，保留已产生的步骤结果 |
| 整流程超时 | 调用方显式值优先于 YAML `flowTimeoutMs`，两者均缺失时拒绝执行；任一已提供值不是正整数毫秒时均报错。记录最终值及来源，从调用 `Interpreter.run()` 起计时。到期调用 `stop()`，追加 `kind: flow`、`status: timeout` 的记录，不再接纳迟到结果 |
| 收尾 | 执行返回（含异常）或超时后的有限等待结束后，均尝试对各参与端调用 `finish()`，逐端记录结果或异常；409 busy 记为收尾失败，不证明 SDK 已停止。一端失败不跳过其他端的收尾，也不覆盖原执行错误 |
| 证据与报告 | 采集命令、事件及运行数据证据，核对必要验证项，保存本次报告；完成采集后释放 HTTP 客户端。各项操作有有限等待上限，保存失败和证据缺口须单独记录 |

`Interpreter.run()` 本身不负责上述宿主超时、finish、证据采集及报告保存。流程内部控制流、引用、断言和事件等待仍由解释器处理；初始化、登录仍是用例命令。

整流程超时后的顺序固定为：`stop()` 并记录超时 → 有限等待原 `run()` Future 返回 → 逐端 `finish()` → 采集证据、保存报告 → 释放客户端及宿主采集资源。等待和各收尾操作分别有明确上限并记录实际值；原 Future 到期仍未返回时记录该事实并继续收尾，不无限等待，也不宣称其已退出。保留迟到异常的处理，已发布报告和用例结论不再被迟到结果改写。

解释器返回或 `finish()` 成功均不保证底层 SDK 副作用已停止；SDK 在途、超时或结果未知的信息随原错误保存。收尾达到上限仍须保存已有结果和证据缺口，后续用例按共享资源的影响决定是否阻断。

**判定规则**：

- 逆向用例按预期 SDK 错误判定；通信、解释器和超时错误不能冒充预期 SDK 错误。
- 事件断言必须包含业务归属及本轮关联条件，不能仅匹配事件名称。按 §4.1 核对必要验证项；必要节点所在分支未选中或节点被跳过，均不能视为该验证通过。其他正常未选分支不单独算失败。
- 执行返回或超时收尾达到上限后，校验报告是本次调用产物：`runId` 等于本轮 ID，`flow` 等于固定 YAML 的 `name`，`startedAt/finishedAt` 可解析且先后合理，`steps` 是结果列表，`summary` 各状态计数及 `total` 与列表一致。保存后以 `FileRef` 登记到本次 `ExecutionResult`，同时绑定用例、执行序号、固定定义和启动标识；汇报核对这些归属及文件摘要，不能仅凭相同 `runId/flow` 接收另一次复验的报告。字段缺失、旧文件或统计不一致均属于无效报告；报告存在不代表在途操作已结束。

结论按下表从上到下判定；本表同时是 CSV 的“是否通过”来源。

| 条件 | 用例结论 | 交付汇报的内容 |
|---|---|---|
| 准入失败，尚未调用运行器 | 未执行 | 缺失条件、责任环节、故障及证据 |
| 解释器异常、外部中断、整流程超时，或报告及判定所需证据缺失／无效 | 未完成 | 原始错误、已有步骤结果和证据缺口；不得生成虚假的成功报告 |
| 解释器正常返回（含按 `onFail` 结束），报告及证据有效，但存在步骤 `failed/timeout`，或必要断言未执行／未通过 | 否 | 对应步骤、预期与实际、失败原因及证据 |
| 解释器正常返回，报告及证据有效，无失败或超时，必要业务断言均执行且通过 | 是 | 报告及断言证据 |

用例结论与收尾结果分别记录。若业务断言、报告及判定证据完整，`finish()` 失败等收尾故障不改写已确定的用例结论，但任务仍报告故障并返回非零；故障影响判定完整性时，用例记为未完成。不能只读取 `ReportCollector.summary()`，也不能用已有 `finishedAt` 掩盖执行异常。报告发布与目录规则见 §5.1。

`abort_flow/abort_all` 是失败策略，不等同于解释器崩溃；按策略结束且证据完整时判“否”。整流程超时则停止调度和接纳结果，优先判“未完成”，即使此前已有失败或全部必要项已通过。步骤自身超时不自动升级为整流程超时。

约束依据：[解释器 API](../../tool/flow_runner/lib/interp.dart)、[报告字段](../../tool/flow_runner/lib/report.dart)、[客户端接口](../../tool/flow_runner/lib/agent_client.dart)、[用例及事件语义](../../tool/flow_runner/README.md)。

### 4.3 故障闭环

详细约定：[用例执行与故障排查](../../testing_v2/docs/2026-11-06-test-execution-troubleshooting.md)。

执行 → 发现问题 → 复验与排查 → 按职责修复 → 复验 → 继续执行。

| 条件 | 处理规则 |
|---|---|
| 正式执行失败 | 必须复验；由 AI／人工检查证据及前置状态后显式发起，开发、调试阶段不强制复验 |
| 故障影响后续用例 | 暂停受影响部分；修复并复验通过后继续 |
| 后续用例不受影响 | 保留失败证据，继续执行不受影响的用例 |
| 用例设计问题 | 在已确认场景和预期内修正用例 |
| SDK、设备、环境、数据准备或工具问题 | 由相应职责方修复，执行环节协调证据、归因和恢复 |
| 暂时无法修复或需要用户决策 | 记录失败或阻塞原因，不无限重跑，不伪装成通过 |

各类故障均纳入闭环；本轮完成不等于全部通过。排查与代码修复按职责进行，不属于用例控制流指令；重大变更遵循协作确认规则。

CLI 每次调用对指定用例执行一次，不自动重跑失败用例，也不自主修复。复验需要恢复前置状态时先调用 `prepare`，再按 §3.4 通过 `launch` 准备新的 App 实例，以 `run <用例.yaml> --run-id <runId> --launch <启动标识>` 显式执行；`run` 重新核验前置条件。复验保留首次记录并增加执行序号，更换初始化配置或账号数据时按 §2.2 创建新轮次。尚未复验的正式失败须在汇报及故障记录中标明“待复验”，此标记不免除复验要求。

### 4.4 故障排查产物

发现故障时即建立 `tmp/<runId>/issue-<序号>.md`，供排查者和对应职责的修复者交接；不等待根因确认或修复完成。序号在本轮内唯一，同一故障的复验继续记录在原文件中。

| 内容 | 必须记录的信息 |
|---|---|
| 定位 | 轮次、阶段；涉及用例时记录用例、执行序号、步骤及设备角色 |
| 复现条件 | 执行入口与参数、用例及本轮输入快照位置、相关设备和业务前置状态；敏感值使用文件引用 |
| 故障与影响 | 预期、实际结果、错误；哪些执行受影响、已暂停哪些操作 |
| 证据 | 日志或结果文件位置，并标明相关行、操作标识或事件序号，不能只给一个目录 |
| 排查交接 | 当前处理状态、责任模块（未定位时明确标注）、已确认事实、待验证假设、已尝试的方法及结果、下一步待办 |
| 修复与复验 | 修复内容及对应变更位置、复验入口、执行序号、结果和证据；未修复或未复验明确标注 |

执行方记录初始故障，排查者补充归因，修复者记录改动，复验方补充验证结果；新增结论不能抹去首次失败和此前尝试。缺少信息时记录缺项，推测不得写成已确认根因。故障的处理状态及关联证据由编排层同步到 `run.json`；Markdown 提供排查细节，不作为清理工具解析处理状态的数据源。

报告过程记录引用该文件及证据，清理遵循 §7 的保护规则。故障解决后，再将可复用的结论沉淀到 `troubleshooting/YYYY-MM-DD-<问题主题>.md`；已有同类记录则更新原文。

## 5. 轮次、产物与日志

### 5.1 轮次与存放

`runId` 格式：`YYYYMMDD-HHmmss-<场景>-<短随机后缀>`，时间使用宿主本地时间。例如 `20261106-152800-presence-a3f9`。单用例取文件名中的场景段，多用例使用 `batch`，独立操作使用 `devices` 或 `build`；实际范围以快照中的输入为准。生成时确保目录未占用，不覆盖已有轮次。

| 内容 | 位置与命名 | Git |
|---|---|---|
| Dart 源码、数据生成脚本 | `lib/`、`scripts/`，文件名使用 `snake_case` | 纳入，生成文件除外 |
| 生成的数据源码 | `lib/accounts.g.dart` | 忽略 |
| 静态用例 | `data/<版本>-multi-<场景>-<positive\|negative>.<yaml\|json>`；同一用例的 YAML、JSON 主文件名相同 | 纳入 |
| 本轮固定用例 | `tmp/<runId>/cases/<用例文件主名>/` 内的 YAML、JSON 原文副本；文件引用见 `CaseDefinition` | 忽略 |
| 本轮临时数据、设备清单、故障记录及日志证据 | `tmp/<runId>/`；私有运行快照为 `run.json`，设备清单为 `devices.json`，故障记录为 `issue-<序号>.md`，日志见 §5.2、证据见 §5.3 | 忽略 |
| 本工具保留的构建副本与缓存 | `build/<runId>/` | 忽略 |
| 本轮报告 | `reports/<runId>/` | 忽略 |
| 故障沉淀 | `troubleshooting/YYYY-MM-DD-<问题主题>.md` | 纳入 |

场景名使用小写英文和连字符。静态用例文件名不包含运行时间或实际设备 ID；轮次目录内的文件名不重复添加时间戳。

同一轮的复验沿用 `runId`，通过用例标识和执行序号区分记录；重新完整执行生成新 `runId`。不增加专门的正式、开发或调试模式管理；正式结果来自独立完整执行的一轮。

执行序号在同一用例、同一轮内从 1 递增；`run` 在静态解析取得合法、无冲突的用例 `name` 后、准入检查前登记，`all` 在逐例准备前登记同一份尝试记录，执行模块继续使用该序号。准备或准入失败也占序号并写 CSV 行，不能复用；独立 `prepare/launch` 只登记操作，不增加用例执行次数。解析失败无法取得合法编号时记录任务输入错误，不伪造用例编号或 CSV 用例行。不同用例的 `name` 与文件主名在同轮中不得冲突。

登记时确定输入及输出位置，原始报告一经保存不覆盖。解释器已启动时，执行模块将已有结果写入 `reports/<runId>/<用例文件主名>/<执行序号>/flow-report.json`；未启动时只保存未执行原因，不创建空的运行器报告。必要验证项核对及收尾结果保存到快照的本次执行记录。汇报使用登记的实际路径，不扫描目录猜测“最新报告”。

`run.json` 是分环节调用及独立清理的机器可读依据，由编排层统一更新，至少保存以下内容：

| 内容 | 约束 |
|---|---|
| 任务状态 | `runId`、运行中／已停止／未知及观测时间；已停止不表示用例通过或故障已解决 |
| 本轮输入 | `environment` 保存固定账号配置；用例列表、`CaseDefinition`、每用例角色映射和本次 `CaseData`；管理凭据只记录源文件位置，不保存值 |
| 前置准备 | 用例、准备操作标识、允许处理的声明及账号对、准备结果和核验文件引用；独立操作不冒充用例执行 |
| 启动连接 | `connections` 保存 §3.4 的启动记录；本次执行引用明确的启动操作标识 |
| 执行记录 | 本轮输入引用、阶段结果、`ExecutionResult` 及错误；原始报告的摘要随本次执行固定，不接受后续换文件后重算摘要冒充原报告 |
| 产物引用 | 产物路径、类型、所属阶段或执行；报告指向所需证据，不能只有未分类目录 |
| 故障状态 | 故障 ID、未解决／已解决、详情文件、关联证据及处理结论和复验记录的引用 |

模块返回操作结果和产物引用，汇报模块返回报告及证据依赖，编排层据此保存快照。故障解决由 AI／人工明确确认并提交处理结论及验证证据后，由编排层更新；一次复验通过不自动解除故障保护。快照中相对路径以 `testing_v2/` 为基准，外部产物使用绝对路径。

快照和报告须完整写入后再发布引用，不能以提前创建的空文件作为完成标记。交付验收结果连同生产方、接收方、操作标识及差异保存到该次操作记录；失败时关联故障文件。写入失败须记录为产物保存故障；内存中已有结果仍保留，但不得宣称该次结果可恢复或报告已完成。

运行中状态在操作结束时更新为已停止；异常退出留下的状态须核验后记录为已停止或未知。任务是否完成、用例是否通过分别由阶段终态及用例结论表达，不从“已停止”推导。报告文件已写入但快照未确认时，恢复操作只校验已登记路径、身份和内容后补记，不重发业务命令。没有终态且无法恢复的执行记为未完成。

### 5.2 日志要求

工具日志写入 `tmp/<runId>/run.log`，执行中持续追加，不等整轮结束才保存。App 和平台日志可保留原格式，按设备角色存放，如 `deviceA.log`；采集记录必须注明设备、来源和采集区间。

| 记录时机 | 必须记录的信息 |
|---|---|
| 每条工具记录 | 带时区的时间、`runId`、阶段、操作标识、发生的动作或结果；涉及用例时补用例、执行序号和步骤，涉及设备时补实际设备标识及已分配的角色 |
| 阶段或模块调用开始 | 本次操作标识、操作内容、必要输入或输入快照位置；必须在实际调用前记录 |
| 调用结束或失败 | 与开始相同的操作标识、结果、耗时；失败保留原始错误和可取得的堆栈，不只写“失败” |
| 宿主命令 | 可执行程序、参数、工作目录、stdout/stderr 内容或文件位置、退出码；未启动、超时或被终止须单独说明，不能伪造退出码 |
| App 命令 | 角色、JSON 命令 ID、流程步骤及绑定、App 实例、操作标识、发出时间、实际结果和断言；客户端暴露协议请求标识时同时记录 |
| 等待事件 | 等待开始、事件名、匹配条件、超时时间及可取得的游标；结束记录匹配事件及序号，或超时和最后观察位置 |
| 暂停、继续及复验 | 原因、影响范围、关联故障记录；复验使用新的执行序号 |

操作标识在本轮内唯一，同一调用的开始、输出和结束共用标识。平台、协议或客户端 API 未暴露的信息标注为不可取得，不编造。当前 `HttpAgentClient` 不返回 HTTP `commandId`，不得从调用次数猜测它，也不得将 JSON 命令 ID 当作协议 ID；执行结果返回才表示命令终态，派发记录不证明服务端已接收。只有开始而无终态的记录表示中断或结果未知，不能计为成功。

记录示例（文本排版仅作示意）：

```text
2026-11-06T16:10:00+08:00 runId=20261106-161000-presence-a3f9 stage=device operation=op-12 role=deviceA device=<UDID> start action=install artifact=<本轮构建副本绝对路径>
2026-11-06T16:10:02+08:00 runId=20261106-161000-presence-a3f9 stage=device operation=op-12 role=deviceA device=<UDID> end result=failed elapsedMs=2000 exitCode=1 stderr=op-12.stderr.log
```

日志中的证据路径相对 `tmp/<runId>/` 解析，引用应指明行号、操作标识或事件序号。日志和报告中的 Token、密码、密钥必须在写入前脱敏，命令参数及 stdout/stderr 同样适用。采集失败或记录缺失须标明证据缺口；判定所需证据缺失时记为未完成，其他采集故障按 §4.2 保留用例结论并单独报告任务故障。

### 5.3 证据与私有数据

每次尝试的证据位于 `tmp/<runId>/<用例文件主名>/<执行序号>/`。执行模块交付下列记录及定位信息，编排层登记实际生成的文件；不存在的文件不发布为有效引用。

| 文件或记录 | 内容与必要性 |
|---|---|
| `run.json` 中的本次输入 | `CaseDefinition` 的源路径、固定副本及摘要，角色绑定、实际 `biz.input`、生效配置、全局初值和启动记录引用；用于解释参数来源，不复用为下次业务执行 |
| `preconditions.json` | 本次前置核验结果；存在声明时为准入必要证据 |
| `trace.jsonl` | 持续保存 `onTrace` 的命令派发、实际结果、绑定及事件观察，收尾补记 `GlobalData.reads` 的引用读取；写入前补执行标识并脱敏 |
| `<role>-events.jsonl` | 从 App 获取的事件 `seq/source/payload` 及实例归属；收尾分页采集，标明采集区间及缺口，事件内容脱敏 |
| `run.json` 中的核对结果 | 每个 required binding 的匹配数量、状态、报告记录位置；事件验证须能定位相应角色的原始事件序号 |
| `flow-report.json` | 本次实际步骤结果及统计，存于报告目录；缺失或无效不能形成通过结论 |

必要证据是：本次输入归属、有效报告、支撑必要断言的实际结果，以及已声明前置条件的核验。事件断言还需对应的原始匹配事件；与判定无关的设备日志缺口单独记任务故障，不自动推翻已有有效断言。保存 trace、引用读取及运行数据时不得跳过脱敏；脱敏只作用于写出副本，不修改解释器内的执行值或断言值。

前置准备的两类文件位于轮次目录，按 §2.5 命名；本次执行记录引用对应准备操作。不得直接挂载含原始凭据的外部证据目录作为本工具的日志或报告。

`run.json` 含账号及控制凭据，属于私有状态文件；生成源码、私有输入与快照在宿主上仅当前用户可读写（文件 `0600`，运行目录 `0700`）。日志和报告不得复制快照原文；分享时只导出脱敏证据。管理凭据及应用 Token 不进入运行快照。使用已知敏感值及字段进行脱敏，错误字符串、命令参数、stdout/stderr 和嵌套结果均适用；生成文件加载输出同样不得进入宿主命令日志。

报告到证据的依赖保存在 `run.json` 的产物清单中，每项记录报告路径、依赖路径及定位信息（记录索引、行号或事件序号）。汇报模块产生依赖列表，编排层保存，清理模块只读取该列表计算保护范围。证据保持原始结构及顺序，敏感值替换为占位值；不能用脱敏为由删除失败记录。

## 6. 汇报总结

详细约定：[汇报总结](../../testing_v2/docs/2026-11-06-reporting.md)。

| 形式 | 本轮报告目录内的产物 | 必须包含的内容 |
|---|---|---|
| 总结 | `summary.md` | 范围、结果汇总、主要问题和待处理事项，不展开过程细节 |
| 过程记录 | 一个或多个文件，格式按需，可混合 | 关键操作、结果、异常、排查、修复和复验过程，关联原始日志及证据 |
| 统计 | `statistics.csv` | 用例编号、平台、单设备／多设备、正向／逆向、预期、实际、是否通过及原因等维度 |

三种形式通过 `runId` 和用例标识关联。每轮独立统计；用例数量与执行次数分开，首次执行与各次复验分别保留，复验通过不能覆盖首次失败。

总结分别展示用例结果与执行、收尾故障。用例通过但 finish 失败时，CSV 保留用例通过结论，总结及过程记录明确收尾失败；不能将本轮汇总为全部成功。

CSV 每行表示一个用例的一次执行，列定义如下：

| 列 | 来源与含义 |
|---|---|
| 轮次、执行序号 | 本轮 `runId`、该用例的执行序号，用于区分首次执行和复验 |
| 用例编号、用例文件 | 编号取流程 YAML 的 `name`，同时记录源文件路径；不得另行生成用例编号 |
| 平台、设备分类、测试方向 | 平台去重排序后以 `+` 连接；分类本次为 `multi`；方向取规范文件名的 `positive/negative`，不从执行结果推断 |
| 预期 | 用例定义的通过条件及断言，不能根据实际结果倒推 |
| 实际 | 本次执行报告中的实际结果摘要 |
| 是否通过 | 是、否、未执行或未完成；后两项不得计为通过 |
| 原因 | 未通过、未执行或未完成的具体原因；尚未确认根因时说明事实及待排查内容 |
| 证据 | 对应本次报告、故障记录及日志的可定位引用 |

用例数按 YAML `name` 去重，尝试次数按已登记执行序号计数，未执行也计入尝试并单列；不得用 CSV 行数冒充用例数。`report` 从快照及登记的报告重新计算，重复执行可替换 `summary.md/statistics.csv`，不能改写原始执行报告。只有开始记录、缺少终态且无法恢复时列为未完成；报告缺失或损坏保留缺项，不删除失败行。

汇报模块验收 `ExecutionResult` 后生成 `ReportingResult`。发布前按 `(runId, caseName, attempt)` 对账：每个已登记尝试恰好一行 CSV，无重复、无遗漏；总结计数与 CSV 一致；预期取本轮固定定义，实际取对应执行；证据引用能定位实际记录。缺失或损坏的输入保留原始记录并报告缺口，不能伪造通过或重跑用例来补原报告。汇报自身生成、对账失败只返工汇报；旧汇总文件不能冒充本次成功。

`dependencies` 登记报告所需的原始报告、固定用例副本和证据；缺失项单独报告并保留其登记，不能以缺失为由解除其他证据保护。编排层验收交付文件的摘要、尝试清单及对账结果后登记；清理接收方按 §7 再检查引用和保护范围。共同的结构及对账校验复用汇报模块的纯校验能力，不在编排或清理模块另写统计规则。

## 7. 必要清理

详细约定：[必要清理](../../testing_v2/docs/2026-11-06-cleanup.md)。

1. 支持选择缓存、日志、构建、报告中的一个或多个类型，或全部类型；运行产物支持按 `runId` 选择轮次。
2. 只删除明确属于所选范围且不纳入 Git 的产物，不将全部 Git 忽略项作为删除清单。
3. 生成的 Dart 源码始终保留，包括 `lib/accounts.g.dart`。
4. 正在执行的任务所需文件、尚待排查的失败证据不得删除；保留报告时同时保留其依赖的必要证据。
5. 选择全部类型仍须遵守以上保护规则。

清理范围必须同时满足产物登记和下表路径约束；同一路径只登记一种清理类型，避免按“缓存”绕过日志保护。

| 类型 | 允许范围 |
|---|---|
| 缓存 | `tmp/<runId>/` 内已登记的运行输入副本及可再生临时文件；不包括人工提供的生成输入 |
| 日志 | `tmp/<runId>/` 内已登记的工具、设备日志及过程证据 |
| 构建 | `build/<runId>/` 内本工具登记的构建副本与缓存 |
| 报告 | `reports/<runId>/` 内已登记的报告 |

不清理 example 的 `build/`、Pods、各工程 `.dart_tool/` 或全局工具缓存；不能通过符号链接越出允许目录。`run.json` 是保护索引，清理过程中保留并更新；仅当该轮无剩余产物、报告引用或未解决故障时才可最后移除，删除结果输出到调用方，不重新创建已清空的轮次目录。

清理以 `run.json` 中的任务状态、故障状态及产物引用计算保护范围：

| 状态 | 清理规则 |
|---|---|
| 任务运行中或无法确认已停止 | 保留该任务所需输入、运行产物及证据；不能只根据进程退出或文件时间推断可删除 |
| 存在未解决故障 | 保留故障记录、复现输入及关联证据；不得解析 Markdown 猜测已解决 |
| 报告保留 | 同时保留该报告引用的必要证据 |
| 故障已明确解决 | 仅解除该故障产生的保护；仍须检查活动任务及保留报告的引用 |
| 快照缺失、损坏或引用不明 | 保留无法确认可删的产物，并说明原因 |

编排层负责维护及解除保护依据，清理模块只消费这些依据并返回删除结果，由编排层更新实际产物清单。跳过受保护项须列明原因，删除失败单独记录，不能删除仍被保留产物依赖的快照。

清理交付 §1.4 的 `CleanupResult`：每个选中路径归入已删除、保留或失败之一，不能遗漏；删除后核验路径确实不存在才列入 `deleted`，原本已不存在时记录该事实。编排层验收清单不重复、范围一致，并复核已删除项不存在后再更新登记。删除失败不移除登记、不解除保护；不因部分成功将操作记为全部成功。

## 9. 交接示例：Presence 订阅与发布

场景：A 订阅 B，B 发布本次唯一状态，A 收到匹配通知。以下走查一个正向用例的完整交接，不代替场景的正向、逆向验收清单。

| 环节 | 本次输入 → 交付及检查 |
|---|---|
| 生成账号 | 指定本地输入 JSON → `accounts.g.dart`，含 A、B 的真实账号 ID/Token；不操作设备 |
| 建立轮次 | 显式选择 Presence YAML、两角色映射 → 快照固定环境、用例及映射；两设备 ID 不同 |
| 准备与构建 | 映射中的实例 → `devices.json`；对应平台构建 → 自有 `build/<runId>/` 副本 |
| 启动 | 设备和构建副本 → 两角色的新连接，保存启动记录；握手均为 accepting |
| 准入 | 用例 JSON 的 `data.unique.presenceDescription` → 本次唯一状态；必要绑定指向 `global.biz.event.presence_received`，前置核验及数据视图准备完成 |
| 执行 | 两端初始化和登录 → A 清除自身对 B 的残留订阅并重新订阅 → B 发布 `$global.biz.input.presenceDescription`；A 等待事件，检查 publisher 为 `$global.account.bob.userId` 且状态内容为本次唯一值，绑定匹配 payload |
| 用例收尾 | 用例按已确认流程退订、恢复原状态及退出；运行器随后逐端 finish。业务清理命令仍属于用例，与 HTTP finish 分开记录 |
| 汇报 | 有效 flow-report、必要绑定恰好一条 passed、匹配事件证据 → 用例结论及 CSV；缺少该通知不能用查询成功代替 |
| 复验与清理 | 按声明恢复并核验前置状态，重新 launch；保留原序号并为复验登记新序号、新业务唯一值，run 显式选择本次启动；清理按类型及引用保护执行 |

发布前若需恢复 B 的原状态，必须先由用例查询并保存实际值，不能从准备配置猜测。具体账号、模拟器和场景清单由调用方及用例确认提供，不固化在工具实现中。
