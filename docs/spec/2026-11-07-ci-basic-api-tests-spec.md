# CI 基础 API 测试规格

## 1. 目标与依据

为基础、行为明确且能重复验证的公开 API 建立长期 CI 回归保护；不以覆盖全部 API 或增加用例数量为目标。

依据：[项目验证架构](../../AGENTS.md#verification-architecture)、[公开 API 入口](../../im_flutter_sdk/lib/im_flutter_sdk.dart)、[现有设备集成测试](../../im_flutter_sdk/example/integration_test/)。协作和文档遵循 [testing_v2/spec.md](../../testing_v2/spec.md) 的范围约束。

## 2. 范围

- 本轮先完成 API 统计、现有覆盖核查和候选筛选，提交用户确认；确认前不编写测试、不修改 SDK、CI 配置或执行工具。
- 后续用例采用 Flutter 集成测试，位于 `im_flutter_sdk/example/integration_test/`，验证 Android、iOS 原生调用链。
- 本轮仅考虑单设备可独立完成的基础行为；是否需要登录、网络或额外业务资源须分别标明。
- 本轮不做：多设备协同用例；Thread、Room、Push 模块用例；`renewToken`、`getUnreadMessageCount`、`clearAllConversationUnreadMessageCount` 用例。
- 本轮不支持主动断网模拟：当前方案没有实现并验证可控的设备断网手段，不将其列为逆向用例或验收能力。
- CI 与 AI 脚本测试保持独立。纯 Dart 模型转换、参数编解码等已适合单元或契约测试的行为，单独标注，不为增加设备覆盖而重复实现。

## 3. 筛选规则

| 条件 | 判断要求 |
|---|---|
| 基础性 | 支撑初始化、会话、消息等常用基础链路，或具有明确长期回归价值 |
| 契约明确 | 可根据公开契约说明输入、预期结果与关键边界；不能只以当前实现或一次观测为依据 |
| 可独立验证 | 单设备约束执行端数量；允许准备其他账号、好友关系和群组等资源，业务验证无需另一运行中的客户端配合 |
| 数据可控 | 必要的数据准备属于用例职责，须核验前置状态，按 §4 的回收范围清理自身数据或恢复原值；不能仅因目前没有准备工具就排除基础 API |
| 结果可判定 | 可验证具体内容、状态变化、规定错误或服务器最终确认；无法形成可靠断言的行为不纳入。须区分服务器最终成功响应与仅提交请求；前者可作为通过依据，后者不能证明业务完成 |
| 执行可重复 | 不依赖历史数据、用例顺序或固定睡眠碰运气；异步完成有明确条件和有限超时 |
| 成本适合 CI | 必要的账号和业务数据准备计入执行成本，优先选择基础、可重复的行为；额外服务能力或复杂编排须说明必要性 |

筛选结论分为“建议纳入”“待核实”“本轮不纳入”，每项有依据。“建议纳入”表示适合开发验证，不表示已证明运行稳定；待核实项若无法建立可靠验证方式，则不纳入。接口新旧、方法数量和现有脚本是否调用过，均不能单独决定纳入。

## 4. 用例设计方法

### 数据准备与结果验证

数据准备参考 [Makefile 的 env-gettoken](../../Makefile) 及其[生成工具](../../im_flutter_sdk/example/tool/env_tool.dart)：沿用账号与 User Token 的获取方式，群组可取自配置中的已有 ID，但使用前须核验存在性和所需成员。该入口透传群组配置，不创建或核验群组；`RUN_ID` 只增加运行环境 JSON，不隔离远端账号和资源。

好友关系准备和恢复使用已有 [REST 资源客户端](../../im_flutter_sdk/example/tool/rest_resource_client.dart) 的查询、添加、删除能力，增删后须双向查询核验；这不作为被测 `deleteContact` 的结果断言。临时群组创建可参考[资源准备工具](../../testing/tools/data/resources.dart)，补足所需成员核验。CI 参考和复用所需基础能力，保持既有数据准备入口行为，不接入 AI 测试编排；凭据获取、资源准备和被测 SDK 断言职责分开。

| 对象 | 准备及验证方法 |
|---|---|
| 消息发送 | 先注册监听，再发送消息；关联本次消息的异步成功／失败回调，验证服务器最终确认。方法返回不替代回调，发送成功不代表接收方已收到 |
| 联系人 | 查询用例建立并核验好友关系后查询列表和详情；删除用例准备好友关系，分别传入 `keepConversation: true/false`，仅以删除 API 成功返回判定通过，不追加 REST、本地列表、监听通知或会话断言，不准备会话和消息；结束后恢复原关系。发出邀请不等于关系已成立 |
| 黑名单 | 保存原状态，添加／移除后分别核对远端与本地列表，再恢复原状态；只验证成员关系，不推断消息拦截效果 |
| 群组 | SDK 创建、远端读取、销毁构成基础验证链路；成员使用明确查询核验，本地查询不能替代远端存在性判断。查询用例独立准备数据，全部本轮新建群均须回收 |
| 会话列表 | 可通过发送消息产生会话；确认发送完成及会话可查询后，核对会话归属和消息内容 |
| 本地消息与用户资料 | 使用确定的消息或字段值，写后重新读取核对内容和归属；明确内存缓存、本地数据库和远端数据来源，避免原对象赋值冒充持久化验证 |

准备是当前用例的前置步骤，不依赖另一个测试用例先通过。使用可识别的本轮数据，交付资源标识和准备核验结果。准备失败时，依赖它的目标行为记为未执行；失败阶段与根因分别记录，准备阶段也可能暴露 SDK 缺陷。

服务端数据已准备并核验后，本地 SDK 查询或同步未达到预期，应记录对应验证步骤失败并排查，不能以“准备失败”为由跳过。验证过程有有限超时并保留观察结果。收尾仅清理本轮创建的资源或恢复修改前状态，失败也保留证据。

### 资源回收

- 测试创建的可回收资源须配套销毁或恢复操作，正常结束和失败收尾均执行并核验，避免重复测试累积无主数据；已有共享资源不得误删。
- 若将 `ChatGroupManager.createGroup` 纳入被测接口，须配套 `destroyGroup` 的用例和销毁结果断言。仅作为查询用例准备而创建的群，也必须在收尾销毁；未确定清理方式前不新增创建型用例。
- 消息和会话作为本轮回收例外，不要求全局销毁测试产生的记录；相关测试及已有本地数据清理、删除 API 的行为验证保留。本地删除不能证明服务端或其他账号的数据已清除。
- 应回收的资源清理失败时，保留资源标识、归属和错误，整轮失败；补救清理成功也不能覆盖被测销毁接口的原始失败结果。

### 正向与逆向用例

- 用例须包含正向和逆向场景，名称或说明标明类型。
- 开发分两阶段：先补充并验证正向用例，完成后再新增逆向用例；现有逆向用例保留并继续回归。
- 正向：合法输入及满足的前置条件，核验预期业务结果，例如服务器确认消息发送、查询到已准备的好友或群组。
- 逆向：主动构造契约明确的非法输入或不满足的业务前置条件，核验规定错误或返回行为，以及契约要求的数据状态；例如未登录调用 Presence 返回 201。不能以“抛出任意异常”判定成功，也不凭猜测设定错误码。
- 执行中意外断网、Token 意外过期、设备故障或准备失败是执行故障，不能冒充设计好的逆向用例通过。缺少明确预期的逆向场景先核实契约，无法验证则不纳入。

## 5. 调研交付与确认

调研须交付：

1. 代码基线、统计口径、各模块接口数量和筛选数量；方法数、用例数分别统计，正向目标、保留逆向和准备方法分开列示；零值边界不能计为完整功能覆盖。
2. 候选 API、拟验证的正向与逆向行为、登录及网络条件、数据准备与清理要求、现有覆盖和缺口。
3. 待核实项、不纳入范围及理由；区分源码事实、设计建议和设备实测结果。

成果：[API 统计与筛选](../refs/ci-basic-api-tests/2026-11-07-api-selection.md)。用户确认候选范围及待核实项处理方式后，才进入用例开发。

## 6. 用例开发与验收

- 保留现有两个测试文件作为主入口：`no_login_presence_test.dart` 组织未登录用例，`single_account_local_test.dart` 组织单账号登录后的用例。
- 用例实现按业务模块组织，必要时拆分文件，由对应主入口注册执行；共用准备与清理只提取当前需要的辅助函数。
- 保留现有用例编号及对应关系，新增编号遵循既有规则；同步用例映射，核验两个主入口包含全部选定用例，CI 继续使用这两个入口路径。
- 按 §4 设计正向与逆向用例；每例明确准备、操作、断言、清理，失败仍执行可安全完成的清理。
- 写操作验证可观察的结果，分页和筛选核验结果集合与边界；仅请求提交、前置准备或收尾成功不能冒充业务断言通过。
- 失败后先复现并核对契约、前置数据和执行证据。确认是用例设计问题则修用例，数据问题修准备，设备或网络问题修对应环境；疑似 SDK 缺陷由 AI 提供证据和归因建议，交用户确认。SDK 或环境问题不得成为修改正确用例、放宽断言、跳过检查的理由。
- 正向阶段完成标准：Android、iOS 分别完整执行两轮，全部选定正向用例通过，现有用例回归通过，准备和清理无未处理故障，方可进入新增逆向阶段。SDK 缺陷阻塞时交用户确认，不改正确预期。
- 新增逆向用例后完成双平台逐模块及完整套件验证，并记录重复执行结果。实际执行编号须与选定清单一致；映射检查通过不能替代实际执行核对，未执行不得计为通过。
- 按 §4 的回收范围单独核验清理结果，不以卸载 App 代替清理证据；业务断言通过但应执行的清理失败时，分别记录两者结果，整轮失败。准备、验证或清理失败时 CI 返回非零并自动结束，人工确认在排查阶段进行。
- 验收记录包含用例编号、平台、轮次、预期、实际、结果、失败阶段和证据；每轮日志独立保留，复验不得覆盖原失败记录，不以少量成功推断稳定率。
