# 自动测试报告

测试结果分两份报告：**CI 持续回归报告**、**版本升级报告**。版本升级报告内分别统计单设备和多设备，不将场景、步骤和 CI 用例数相加。每次运行的报告和证据均在 Git 忽略目录；本文件只说明生成方法和统计规则，不保存运行结论。

报告生成使用 Python 3 标准库，无需安装 Python 包。既有测试入口自动生成报告并打印路径；只读重建报告不会执行测试，也不代表获得新一次验证结果。硬终止（SIGKILL、断电）可能来不及生成汇总，保留的原始结果可用于重建，缺少结束记录不能判通过。

## CI 持续回归

从仓库根执行：

```bash
# 各入口执行自己的全部范围；nightly 为四个初始化批次。
bash tool/ci/nightly_local.sh android
bash tool/ci/smoke_local.sh ios
FORMAT_BASE_SHA=HEAD bash tool/ci/run_quality.sh

# 单个用例：--name 正则通过 CI_TEST_NAME 传入原有设备 runner。
CI_TEST_NAME=FL-APP-001 bash tool/ci/run_android_emulator_test.sh \
  integration_test/no_login_presence_test.dart android-single-case.log
```

Nightly 账号配置沿用 `E2E_CONFIG_PATH` 或原有环境变量。单个登录用例仍需 `E2E_CONFIG_PATH`。`CI_TEST_NAME` 也可用于 quality 的 SDK 单元测试，筛选测试名称；静态检查仍按原流程执行。直接裸跑 `flutter test` 不会调用本仓库报告器，应通过上述入口运行，或自行保留 `--file-reporter json:<文件>` 并提供报告运行元数据。

| 输出位置 | 用途 |
|---|---|
| `artifacts/ci/<run-id>/summary.md` | 给人阅读：总数、通过、失败、跳过、未完成、未执行；批次及用例明细、失败断言、耗时和证据链接 |
| 同目录 `report.json` | 同一统计的结构化结果，供 AI／工具读取 |
| 同目录 `run.json` | 单批次的时间、目标、平台、设备、包版本、提交、选择条件、可采集的显式初始化配置及尝试退出码 |
| 同目录 `runner.log` | 准备、构建、运行与报告过程的终端输出 |
| 同目录 `attempt-N.events.jsonl` | Flutter JSON reporter 原始事件；统计依据 |
| 同目录 `attempt-N.log` | 第 N 次尝试的原始测试输出；重试不覆盖首次证据 |
| `artifacts/<原有日志名>` | 保留原有兼容日志位置；正式追溯以独立运行目录为准 |

Nightly 的顶层 `summary.md` 汇总四批，各批次报告和证据在其子目录。一次失败不阻止后续批次，最终命令仍返回失败。GitHub Actions 现有 artifacts 同时上传 `artifacts/ci/`。

统计规则：

- 单位为“用例 × 平台 × 初始化批次”。相同 ID 在不同配置下执行分别计数，同时显示已观察到的去重用例数。加载、`setUpAll`、`tearDownAll` 归入准备／收尾，不计业务用例。
- 总数来自 Flutter 当前选测的根 group 数量；通过/失败/跳过依据 `testDone`。开始但没有结束为未完成；已发现但未启动为未执行。构建／启动失败导致尚未发现用例时，总数显示未知，并明确批次异常，不能称空集合通过。
- 自动重试只取最后一次尝试进入总计，所有历史尝试及失败保留。用例内 `addTearDown` 失败按 Flutter 结果计入该用例，报告不猜测其业务断言是否已成功。
- 初始化字段来自本次入口源码的显式字面配置，不表示 native 已回读；未采集字段和实际 native 解析版本不伪造。
- 定向执行明确列出过滤条件，不宣称完整回归。报告不改变测试退出码语义或重试策略。

重建或汇总显式指定的独立批次：

```bash
python3 tool/ci/report.py render --run artifacts/ci/<单批次运行目录>
python3 tool/ci/report.py merge --output artifacts/ci/<汇总目录> \
  --run artifacts/ci/<批次一> --run artifacts/ci/<批次二>
python3 tool/ci/report.py --help
```

不自动遍历历史目录。同平台同初始化入口的重复运行禁止直接相加，应显式选择要采用的那次运行；其他运行的独立报告保留。Nightly 重新汇总时逐个指定四个子目录。

## 版本升级：单设备与多设备

单设备 `make auto-report`，多设备 CLI 的 `all`、`run`、`report` 均产出本次范围的 `upgrade-report.md` 和 `upgrade-report.json`。全量与单项沿用同一报告规则：单设备通过 `SCRIPT` 选择脚本，多设备通过选择清单或 `run --case` 选择场景，不为报告增加测试调度入口。

| 分类 | 自动报告目录 | 统计单位和原始证据 |
|---|---|---|
| 单设备 | `reports/5.0.0/<run-id>/` | 一个 JSON 脚本为一个场景；步骤另计。关联 `run.json`、`steps.json`、`events.jsonl`、`crash.log`、`issues.md` |
| 多设备 | `testing/multi/reports/<run-id>/` | 一套协同流程及角色设备组合为一个场景；设备数不算场景数。关联 `statistics.csv`、`process.json`、各场景 `flow-report.json` |

单设备目录名 `5.0.0` 是现有工具输出约定，不证明实际 native 版本。版本报告分别显示两类场景的总数、通过、失败、跳过、未执行、未完成，以及独立的步骤统计；未纳入的类别明确说明本次未选，不计通过。逆向符合预期的错误属于通过。业务验证与清理情况分别呈现，失败或未完成的清理不能显示为无异常通过。

版本升级可能分多轮完成。通过显式运行目录汇总为一份报告，不自动扫描历史：

```bash
python3 testing/report_upgrade.py --version 5.1.0 \
  --single reports/5.0.0/<单设备正向运行> \
  --single reports/5.0.0/<单设备逆向运行> \
  --multi testing/multi/reports/<多设备运行> \
  --output reports/5.1.0/<本次汇总目录>
```

也可只传一个 `--single` 或 `--multi` 重建单次报告。版本参数是验收标签，不替代依赖版本证据。具体执行前置、单次运行及结果文件见[单设备入口](../../testing/single/README.md)和[多设备入口](../../testing/multi/README.md)。

## 先看报告，再看证据

1. 先打开终端打印的 `summary.md`（CI）或 `upgrade-report.md`（版本升级）。
2. 确认报告的运行范围、平台、配置和结果分类；不要将“本次选测通过”理解为所有版本能力通过。
3. 从失败用例／场景的链接进入结构化步骤和原始日志。分享或归档时保留这些相对路径对应的证据文件。
4. 原始数据缺失会限制重建能力；不要仅保留汇总后删除证据，再把失效链接视作完整报告。
