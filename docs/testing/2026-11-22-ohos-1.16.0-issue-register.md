## 问题清单

### ISSUE-1 多端群组事件未知 event 码击穿 test binding（A 级，已修复）

- **现象**：contact 套件运行中 `_onMultiDeviceGroupEvent` 抛 `Null check operator used on a null value`（chat_client.dart:146），platform channel 处理器异常导致该套件后续全部用例 "did not complete"。
- **复现率**：3 轮全量中 2 轮出现（1.15 native 1 次、1.16.0 第 1 次），2 轮插桩全量 0 出现；插桩（打印原始 event 码）两轮均未抓到事件送达，属服务端延迟投递触发，非必现。
- **已确认事实**：
  - native 1.15.0 / 1.16.0 的 `.d.ets` `MultiDevicesEvent` 声明完全一致（2-6 / 10-33 / 60-64），其中 30-33 曾缺失于 Dart converter（本次已修，见 A-1）；
  - 首崩发生在 converter 已补 30-33 之后 ⇒ **崩溃码不在声明枚举内**；
  - ArkTS 侧 `event as number` 是强转不是转换，native `.so` 理论上可透传声明外的码（如服务端驱动的更新事件类型）；
  - `libhyphenate.so` 符号已剥离，无法离线枚举实际码表。
- **根因结论**：Dart 侧 `convertIntToChatMultiDevicesEvent(...)!` 对未知码无防御，平台通道处理器抛异常中断整个套件。ArkTS wrapper 与 4.x Android wrapper 均为原生 int 透传（`event as number` / `data.put("event", event)`），wrapper 无缺陷；native 透传声明外事件码属鸿蒙 native SDK 侧问题（服务端推送新事件类型时旧 native 无白名单过滤），Flutter 层无法补语义，需提工单给 native 团队。
- **影响**：单事件即可团灭一个套件（级联 "did not complete"）。
- **修复**：chat_client.dart 三个多端 handler（group/contact/conversation）统一走 `_parseMultiDevicesEvent`——converter 返回 null 时 `ChatLog.e` 记录原始 event 码并丢弃事件，不再崩溃（用户裁决：未知事件不处理、error 级日志，不降级为 UnKnow 分发）。修复后 nightly 日志可直接抓到原始码，用于 native 侧定位。

### ISSUE-2 FL-EVENT-205 群成员加入回调超时（C 级 → 拆分为两种模式，分别提工单）

- **现象**：等待"本设备用户 A 加入 peer 所建群"的 `onMemberJoinedFromGroup(groupId, A)` 40s 超时。
- **复现率**：高（多轮出现）。
- **模式一（服务端投递延迟）**：预期事件迟迟未到；旁证为崩溃轮中 REST 群操作产生的事件被延迟 1-3 分钟投递到 A 端（落在 contact 套件时段）。token 级别已确认：REST 全部走 app 级 token（`grant_type: client_credentials`，`rest_fixture.dart:398` Bearer 头），按服务端规则通知应当产生。
- **模式二（native member 错值，2026-11-22 轮 20261122120652 实证）**：事件 1 秒内即送达，但 `member` 字段是**群主**而非被拉入的 A——服务端 SYNC meta 明确 `DIRECT_JOINED, tos:[A]`，经 wrapper/Dart 逐层透传后 Dart 收到 `member=群主`。wrapper（`GroupManagerWrapper.ets:991`）与 Dart（`chat_group_manager.dart:121`）均为原样透传，错值产生于鸿蒙 native 1.16.0 对 DIRECT_JOINED 的成员解析（疑取同批次 SYNC 首条 meta 的 `from`，该条恰为群主的 PRESENCE）。**历史轮日志磁盘副本已不存在，旧轮"无关延迟事件"是否实为模式二（groupId 属于本用例但 member 错值）已无法回验**；崩溃轮的"延迟 1-3 分钟"证据独立于本用例，仍支持模式一存在。
- **处置**：两种模式分别提工单（见工单 2 / 工单 3）。
- **结案（2026-11-24）**：工单 3（HIM-24345）经 emclient core 源码定位确认为**非 bug**——`EMGroupManager::handleMUCOperation`（emclient `src/emgroupmanager.cpp:2689`）按 `from==loginUser` 分流，本端自己的 PRESENCE 被自分支吞掉，`onMemberJoined` 设计上永不上报自己；观察到的 member=群主来自 PRESENCE 分支 `from` 回退（:2848），DIRECT_JOINED 走 `onAutoAcceptInvitationFromGroup`（无 member 参数）。用户结论"问题不成立，关闭"。FL-EVENT-205 测试预期已修正：等待 `onAutoAcceptInvitationFromGroup(groupId)`（本端被拉群）+ `onMemberJoinedFromGroup(groupId, member=群主 ciPeerId)`（群主 presence）。模式一（投递延迟）11-23 全天 0 复现，维持暂缓。

### ISSUE-3 FL-CONV-030 按时间删除本地及服务端消息（C 级 → 服务端问题，提工单）

- **现象**（两种模式）：
  - 旧模式：首轮轮询即抛 `TimeoutException after 0:00:00.068`，间歇出现（日志已失，未回验）；
  - 新模式（2026-11-22 轮 20261122120652 实证）：删除被服务端接受且广播通知、本地删除成功，但按时间删除后的服务端历史索引 **≥19.6 秒未生效**（20s 轮询窗口内每条历史响应仍含被删消息），用例超时。
- **复现率**：多轮出现。
- **归因（新模式，证据链闭环）**：服务端漫游索引对 `deleteTime` 类删除的传播延迟。同轮对照：按消息 ID 删除（deleteMsgId）亚秒内传播（FL-CONV-029 当轮通过；teardown 的 deleteRoamById 响应+回推通知 <300ms），`deleteTime` 类 20s+ 未传播——非全局服务慢，是删除类型相关的索引传播问题。与 FL-MSG-022 已标记的 UNVERIFIED（"multi-minute roaming index delays"）同类。
- **处置**：提工单（工单 4）；测试侧暂不修改，待服务端结论后决定是否与 MSG-022 同改为 UNVERIFIED 只验 REST 成功。

### 工单 4：服务端漫游消息按时间删除（deleteTime）索引传播延迟 ≥20s（按 ID 删除亚秒达）（✅ 已提交 HIM-24346，2026-11-23；指派人由用户手动设置）

- **项目**：HIM，归属服务端（IM 漫游消息索引）。
- **环境**：同工单 3（appkey `easemob-demo#zuoyu`，A=`zuoyu01`，对端会话 `zuoyu01_ci_peer`）。
- **问题描述**：SDK `deleteLocalAndServerMessagesByTime` 删除服务端漫游消息，服务端 REST 响应 `ok`、并向其他设备广播 `roaming_delete/deleteTime` 通知，但此后 **≥19.6 秒内每次拉取服务端历史仍返回已删除的消息**（每 600ms 轮询，20s 窗口内无一次例外）；按消息 ID 删除（deleteMsgId）在**同一轮、同一账号、同一会话**内亚秒级传播（FL-CONV-029 当轮通过，teardown 的 deleteRoamById 响应+回推通知 <300ms）。延迟非全局服务慢，而是与删除类型（deleteTime）强相关。同套件 FL-MSG-022 已主动标记 UNVERIFIED 观察同类现象（"multi-minute roaming index delays"）。
- **最小复现步骤**：
  1. A 端 SDK 登录，向会话 C（单聊对端）发送一条文本消息，记录 `serverTime`；
  2. A 端调用 `deleteLocalAndServerMessagesByTime(beforeMs: serverTime + 1)`（会话 C）；
  3. 循环调用 `fetchHistoryMessagesByOption(C, pageSize: 50)`（间隔 600ms）检查该消息是否消失；
  4. 预期：与 deleteMsgId 同级时延（亚秒～1s）；实际：≥20s 未消失（本证据链 19.6s+ 后测试超时退出，无法观测到最终生效时刻；teardown 按 ID 删除污染了后续观测）。
